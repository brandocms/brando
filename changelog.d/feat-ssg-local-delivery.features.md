- A static site can be served by the installation itself: with the deploy strategy "Served by this installation" (`:local`), a deploy or rollback records the build as published, and the live environment's domain answers from it on the next request, on every node, with its 404 page for a path the build lacks and for one that reaches Phoenix there and no route answers, its redirects, `ETag` revalidation, a year's caching for content-addressed assets, the browser security headers on its pages and a telemetry event per request; a live switch moves the domain to the incoming environment, and the domain keeps answering from the published build until the next deploy.
  Run `mix brando.gen.migrations` for `brando_230`, then `mix brando.migrate` (in a release, `bin/my_app eval "MyApp.ReleaseTasks.migrate()"` from the new release) before the new release starts; with tenancy enabled the application does not start until it has run. With several nodes, keep `sites/` on storage they all share. Keep the web module's `static_paths/0` the same list as the `only:` of the endpoint's `Plug.Static`, which the System check's new "Static paths of served builds" compares: a release file under a prefix only `only:` names is answered with the build's 404 page. List an application's own paths that must keep reaching Phoenix on such a host with `config :brando, Brando.SSG.LocalDelivery, dynamic_paths: ["/api"]`, set a Content-Security-Policy of the application's own for its pages with `config :brando, Brando.SSG.LocalDelivery, headers: %{"content-security-policy" => "…"}`, and refuse the strategy and its deploys for every site with `config :brando, Brando.Sites.DeployConfig, local_delivery: false` (a site already published keeps answering from its build until its strategy is changed).

- A static build's `_redirects.json` names the languages and default language the build was made with (`languages`, `default_language`), so a host reads each path's language as the build did.
