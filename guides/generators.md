# Installation and generators

Install Brando into a standalone Phoenix application through Igniter, review the
source diff, then build assets and initialize the database. Existing Phoenix
routes, templates, tests, configuration, secrets and dependency choices are
preserved. Conflicting generated files stop the plan, including with `--yes`.

The admin's JavaScript and CSS, BrandoJS (`@brandocms/brandojs`), is
published to npm with every Brando release at the same version, and a released
Brando installs it from there. Development versions (`-dev`) have no npm
release and take BrandoJS from the Brando checkout through Yalc; see
[Build assets](#build-assets).
The working consumer combination is phx_new 1.8.13, Phoenix 1.8.15, LiveView 1.2.12,
Elixir 1.20.4, OTP 28.5.0.8 and PostgreSQL 16.1. Install Node.js 24, pnpm, PostgreSQL, the matching
Phoenix generator and an Image/Vix-supported build environment first, and Yalc
to take BrandoJS from a checkout.

The old `install.sh` entry point is retired and prints these instructions without
changing the application. Use the commands below for a reviewed installation.

## Create or select a Phoenix application

From outside an existing Mix project, the qualified one-shot development bootstrap is:

```sh
mix archive.install hex phx_new 1.8.13
mix archive.install hex igniter_new 0.5.28
mix igniter.new studio --with phx.new \
  --with-args="--no-install --no-assets --no-dashboard --no-mailer" \
  --install brando@path:/absolute/path/to/brando
```

This installs the admin and the CMS public site, which takes `/` from
phx.new's homepage (see [Add CMS public pages](#add-cms-public-pages)). To
keep Phoenix's homepage and install the admin alone, install with
`--no-public-site`: `mix igniter.install brando --no-public-site`, which passes
the flag on to Brando's installer, or `mix brando.install --no-public-site`
once Brando is a dependency.

The archive supplies Igniter and invokes Brando's installer. Brando's optional
modules automatically recompile if Igniter is added to an already compiled
consumer. The one-shot archive currently fails when launched from inside an
existing Mix project on the qualified Elixir version; create the new application
from its parent directory. Existing applications use the package command below.

Alternatively, create Phoenix explicitly:

```sh
mix phx.new studio --no-install --no-assets --no-dashboard --no-mailer
cd studio
```

Use a Phoenix generator compatible with Brando's dependency constraints. For
example, older generators selecting LiveView `~> 1.1.0` cannot resolve Brando's
current LiveView 1.2 dependency. `phx_new` 1.8.13 selects `~> 1.2.0` and
resolves.

An application generated by an older `phx.new` reports this when fetching:

    Because "your app" depends on "brando" which depends on
    "phoenix_live_view 1.2.12", "phoenix_live_view 1.2.12" is required.
    So, because "your app" depends on "phoenix_live_view ~> 1.1.0",
    version solving failed.

No installer can repair this: resolution fails while fetching, before Brando is
compiled and before any of its tasks can run. Widen the constraints your
application declares, then fetch again:

```elixir
{:phoenix, "~> 1.8.13"},
{:phoenix_live_view, "~> 1.2.0"},
{:ecto_sql, "~> 3.14"},
```

A lock built for the previous constraints also blocks resolution; run
`mix deps.unlock --all` before `mix deps.get` when the reported conflict names
`the lock`.

Add these dependencies to the consumer's `mix.exs`, using your actual checkout:

```elixir
{:brando, path: "/absolute/path/to/brando"},
{:igniter, "~> 0.8.0", only: [:dev, :test]}
```

Then run:

```sh
mix deps.get
mix deps.compile
mix brando.install
```

Or use Igniter's package installer with the same development source:

```sh
mix igniter.install brando@path:/absolute/path/to/brando
```

While Brando is a path dependency, a running site doesn't pick up changes in
the checkout: the site builds its own copy of the dependency, `mix compile` in
the Brando repository doesn't touch it, and Phoenix's code reloader only
recompiles the site's own code. Adding `:brando` to the endpoint's
`reloadable_apps` does make the reloader compile Brando's edits, but it checks
Brando's whole source tree (about 1,600 files) on every request: 40 to 70 ms
on Elixir 1.18, and on 1.19 and later every request also rebuilds the site's
consolidated protocols, 0.6 to 3 seconds. Leave `:brando`, and every other
dependency, out of `reloadable_apps`. After changing Brando:

```sh
mix deps.compile brando   # in the site
# then restart the server
```

Admin JavaScript and CSS come from the checkout through Yalc while the site's
admin takes BrandoJS from a local source (`mix brando.assets.setup --local`;
see [Build assets](#build-assets)): run `npx yalc publish` in Brando's
`assets` after a change. The admin's Vite dev server pulls each publish, so
with HMR on there is nothing else to do. Without it, rerun
`mix brando.assets.setup --backend-only` to rebuild. The admin's CSS and the
site's build with native EuropaCSS, which pnpm installs from npm (see
[Native EuropaCSS](migrating_from_053.md#native-europacss) and
[Site frontend](migrating_from_053.md#site-frontend)).

The package installer calls the same `brando.install` task. Preserve your selected
Git/path source while testing unreleased work; a bare `igniter.install brando`
selects the package source according to Igniter's own dependency rules. Brando's
installer does not replace your dependency with a hardcoded relative path.

The generated changes configure Brando, extend supervision/endpoint/router,
create the admin support modules and Vite projects, and add missing migrations.
A new install adds the CMS public pages described below unless given
`--no-public-site`; a homepage the application has made its own is kept, and
a router the site can't be added to keeps its routes and gets the admin alone.
For a [Florist deploy](deployment.md), the installer writes the production
endpoint's `check_origin`, the Florist environment files and the
release script that sources them (see [Deployment hosts](#deployment-hosts)),
Brando's Dockerfile and `.dockerignore` when there are none,
`MyApp.ReleaseTasks` and a release that writes the tarball Florist deploys,
relative `media_path` and `log_dir` in `config/prod.exs`, and the
`.gitignore` lines a Brando application needs. The release does not copy
`priv/static`, so phx.new's `favicon.ico` there is removed and its
`images/logo.svg` moves to `assets/frontend/public/images`; with the public
site, its `robots.txt` is removed too, so Brando answers
`/robots.txt`. "Release helpers", "Media and
log paths", "Ignored files" and "The Docker build" in the deployment guide
describe each, and what an existing file keeps. Florist's own configuration,
like sample content, remains separate.

The installer also adds `:brando` to `import_deps` in `.formatter.exs`, so
`mix format` keeps Blueprint DSL calls without parentheses, and moves the
application's version to a `VERSION` file that `mix.exs` reads
(`@version "VERSION" |> File.read!() |> String.trim()`), where Florist looks
for it. A literal version, inline or in `@version`, moves; an existing
`VERSION` is kept, and `mix.exs` reads it when the two agree, with a notice when
they don't. A `mix.exs` that computes its version another way is left as it is.

A new install pins the toolchain above in a `.tool-versions`, which asdf and
mise both read: Erlang 28.5.0.8, Elixir 1.20.4, Node.js 24 and pnpm 10.32.1 (the
Node.js major and pnpm the Dockerfile's asset stages use). With asdf or mise,
`mix` and `pnpm` in the application then run those versions whatever the
machine's defaults are; run `mise install` or `asdf install` for the Node.js
and pnpm it names. The file is written only when the install itself runs the
Erlang and Elixir that asdf or mise installed under those names (an Elixir
from Homebrew, or one asdf built from source as `1.20.4`, doesn't count),
since the install's follow-up `mix` tasks run in the application and a shim
stops at a pinned version it has not installed under that name, and only
when neither the application nor a folder above it (below your home folder)
pins a toolchain already: a `.tool-versions`, a mise configuration
(`mise.toml`, `.mise.toml`, `mise.local.toml`, `.mise/config.toml`,
`.config/mise.toml`, `.config/mise/config.toml`), `.nvmrc` or `.node-version`.
Otherwise a notice shows the file's contents to add yourself.

## Choose configuration

A new install defaults to `none` without a prompt. Omitted flags on a rerun keep
the existing mode and site key. Other choices are:

```sh
mix brando.install --tenancy-mode single --site-key studio
mix brando.install --tenancy-mode multi
mix brando.install --interactive
```

`--interactive --tenancy-mode single` asks only for the missing site key.
`--yes` accepts the diff; it neither enables guided questions nor permits replacing
conflicting files. `--dry-run` previews source without applying it. In a
terminal, `--dry-run` asks how to show the diff, and option 1 prints all of it.
Without a terminal, `--dry-run --yes` prints only the moves and removals of an
install-sized diff. To review the whole change, commit the application before
installing, install, and read `git diff` (with `git status` for the new files).
`--no-tenancy-prompt` remains supported.

Review `config/brando.exs` and your existing Phoenix database/endpoint settings.
The default language is English. Add languages deliberately before initializing
content. Follow [Sites and environments](tenancy_and_environments.md) when using
`single` or `multi`; changing the source setting does not migrate existing data.

The installer discovers custom namespaces and allows `--module`, `--web-module`,
`--admin-module`, `--repo`, `--router` and `--endpoint` selection. Ambiguous modules
and unsupported application layouts produce instructions before files are written.
Umbrella roots are not currently supported.

Existing `/admin` routes, dynamic route paths and conflicting authentication
migrations require explicit integration. Brando owns the shared public `users`
and `users_tokens` tables; the installer does not rename an existing account
schema. Preflight examines source declarations, without inspecting a live database.

## Deployment hosts

```sh
mix brando.install --domain example.com
mix brando.install --domain example.com --staging-domain preview.example.net \
  --origin '//*.agency.example' --origin 'https://cms.example.org:8443'
```

`--domain` is the production domain and `--staging-domain` the staging host,
by default `staging.<domain>`. `--origin` adds a trusted origin and can be
repeated: `//host`, `//*.host` or `http(s)://host`, each with an optional port;
a wildcard needs at least two labels after it (`//*.example.com`, not
`//*.com`). A domain is a bare host name, without a scheme, port or path, and
not an IP address. Invalid values stop the install with an issue.

The installer writes:

- With `--domain`, `check_origin` for the endpoint in `config/prod.exs`:
  `//<domain>`, `//*.<domain>`, `//<staging host>`, each `--origin`, and the
  `PHX_HOST` of any `.envrc.prod` or `.envrc.staging` already there. Staging
  runs the prod release with its own environment file, so its host is listed
  here too. The list replaces Phoenix's default check against the endpoint's
  URL host, so add any other host the application serves.
- `.envrc.prod` and `.envrc.staging` for Florist, with `PHX_HOST` set to the
  domain and the staging host, `PHX_SERVER`, a `SECRET_KEY_BASE`, a
  `DATABASE_URL` and a `RELEASE_NODE` default. They use the names a Phoenix
  `config/runtime.exs` reads and are added to `.gitignore` because they hold
  secrets. The diff and `--dry-run` show markers in place of the secrets,
  which the installer fills in after you accept the changes.
- `rel/env.sh.eex`, which makes the release source the environment file
  Florist copies into it (`.envrc.runtime`) and sets long node names.

Prod connects as `<app>`, Florist's default database user, and staging as
its own `<app>_staging`: Florist takes one password per target, and a role
both targets share keeps the password of whichever was set up first. Set the
staging target's database user in `florist.config.exs`
(`set :user, "${PROJECT_NAME}_staging"`), and `FLORIST_DB_PASSWORD_PROD` or
`FLORIST_DB_PASSWORD_STAGING` to the password in the `DATABASE_URL`. Build the staging target with `set :mix_env, :prod`, not
the `:staging` in `florist init`'s example: the application has no
`config/staging.exs`, and the prod `check_origin` is what lists the staging
host. See "Runtime environment" in [Deployment](deployment.md).

Without `--domain`, no `check_origin` is written, so Phoenix keeps checking
origins against the endpoint's URL host, which `PHX_HOST` sets. The
environment files get placeholder hosts built from the application name
(`my-app.com`, `staging.my-app.com`) and the installer says so. With
`--interactive` and no `--domain`, it asks for the domain, then the staging
host and, when `check_origin` is still to be written, the extra origins
(comma-separated), skipping any an option answers, and asks again after an
invalid answer; an empty domain answer keeps the placeholder. `--yes` and a
plain run never ask.

An existing `check_origin` in `config/config.exs`, `config/prod.exs`,
`config/runtime.exs` or a file they import with a literal path, an existing
`.envrc.prod` or `.envrc.staging`, and an existing `rel/env.sh.eex` are kept:
reruns change none of them, and asking for different hosts adds a notice with
the values to set by hand. A kept `rel/env.sh.eex` that does not source
`.envrc.runtime` gets a notice too.

## Add CMS public pages

A new `mix brando.install` adds the public site; `--no-public-site` leaves it
out. A rerun never adds it. To add it to an application installed without it:

```sh
mix brando.gen.site --replace-phoenix-home
# or, with guided homepage ownership:
mix brando.gen.site --interactive
```

The site is `YourWeb.CMS.PageController`, `PageHTML`, `Layouts`,
`SiteContext`, the [lockdown](#lockdown) page, the site's
[error pages](#error-pages) and a [live preview](live_preview.md) of pages.
Its pipeline resolves the tenant before locale and identity;
published pages use the built frontend assets, Brando metadata and named page
routes. Explicit application routes take precedence over CMS catch-all routing.
phx.new's `priv/static/robots.txt` is removed while it is unchanged, with
`robots.txt` in the web module's `static_paths/0`, so `/robots.txt` is the SEO
settings' text in development as in the release; a changed one is kept, with a
notice.

On a new install, phx.new's `PageController.home` route at `/` is replaced while
`PageController` and its `home.html.heex` are still as `mix phx.new` wrote them.
A homepage the application has changed is kept, and the site is not generated,
with a notice naming the `mix brando.gen.site` commands above; `--interactive`
asks instead. `mix brando.gen.site` removes the route only with
`--replace-phoenix-home` or an affirmative interactive answer. The controller and
templates remain available. Other homepages (a LiveView at `/`, or Phoenix
1.6's `PageController, :index`), catch-alls, routes whose first segment is a
parameter (`scope "/:locale"`, `get "/:slug"`), support-path collisions and a
router without a `:browser` pipeline, which the site's routes pipe through,
need manual integration: a new install leaves the site out and installs the
admin, with a notice naming the routes and the `mix brando.gen.site` command to
run once they are resolved, and `mix brando.gen.site` stops. `--yes` never takes
ownership of a changed homepage. Update
existing homepage request-test expectations when replacing the homepage
behavior; phx.new's own test of it is removed with the route.

After database and account setup, use `/admin/pages` to create and publish a Page
with URI `index`, marking it as the homepage and choosing `index.html`. Other pages
can use `default.html`. The scaffold configures `:page_html_module` to select its
own CMS templates while preserving your Phoenix PageHTML and layouts. Templates
under `priv/templates/brando.gen.site` override packaged defaults. No page or
account is created by this source generator.

### Error pages

The site's 404 and 500 pages render in its layout, `YourWeb.CMS.Layouts`.
phx.new's `YourWeb.ErrorHTML`, which `render_errors` in `config/config.exs`
names, is replaced while it is unchanged from what phx.new generated, and the
404 and 500 templates go in `controllers/error_html/` next to it. Other
statuses still render their status message as plain text. phx.new's
`error_html_test.exs`, which asserts the plain-text pages, is replaced too.
Both are recognized as phx.new 1.7 and 1.8 generate them. A customized
`ErrorHTML` or test is kept, with a notice.

A missing CMS page (with `use_default_errors: true`, the installer's default)
renders the 404 inside the layout the page already has. An error the endpoint
renders, such as a 500, gets the whole layout, built from the request as it was
when the error was raised. If the layout itself raises, for example while the
database is down and the caches are cold, the page renders without it and the
layout's error is logged.

### Live preview

The generator gives `YourWeb.LivePreview` a `preview_target` for
`Brando.Pages.Page` that renders the edited page as `CMS.PageController`
does: `CMS.PageHTML` and the page's template inside `CMS.Layouts`' root
layout, with the identity, the `main` navigation and the `partials`
fragments assigned. Changing the page's language recomputes those and
re-renders the page's body, header and footer included; `<html lang>` and
`<head>` update when the preview reloads. The module `brando.install`
writes, which has no targets, is replaced; a missing one is created. A
LivePreview that already previews pages is kept, and any other customized one
gets a notice with the target to add. See [Live preview](live_preview.md) for more views and assigns.

### Lockdown

`Brando.Plug.Lockdown` keeps a site under construction private. The generator
puts it first in the `:brando_site` pipeline and adds the page it sends
visitors to: `YourWeb.CMS.LockdownController` and `LockdownHTML` at
`/coming-soon`, routed through `:browser` only, with the route name
`lockdown`. The installer writes `lockdown: false`, so the plug passes everyone
until you turn it on:

```elixir
# config/runtime.exs
config :brando,
  lockdown: true,
  lockdown_password: System.get_env("LOCKDOWN_PASSWORD"),
  # Optional: the site opens by itself after this time.
  lockdown_until: ~U[2027-01-01 00:00:00Z]
```

While locked, signed-in users with access to the admin see the site: with
groups authorization, those whose groups grant backend access; with legacy
roles, every active account, as for `/admin`. So does the admin's live preview, and
shared preview links (`/__p__/…`) stay open to anyone who has one. Visitors who
enter the password on `/coming-soon`, or open any page with `?key=<password>`,
see the site for the rest of their session. Without a password, or with an
empty one, only users with admin access get in. `/coming-soon` resolves the
site itself, so in multi-site mode it renders with that site's assets. Only
routes through `:brando_site` are locked: add `plug Brando.Plug.Lockdown` to
any other pipeline that serves public pages. The static site generator fetches
pages over HTTP without a session, so turn lockdown off before building a
static site.

An application that already routes `/coming-soon` keeps its own page: the
generator adds neither the page nor the plug, and says so. Rerunning
`mix brando.gen.site` on a site generated before the lockdown page adds both,
as long as what the generator owns (`CMS.PageController`, `PageHTML`,
`Layouts`, `SiteContext` and the CMS routes) is still as it generated it. A
customized one is reported as an issue and the rerun writes nothing; add the
lockdown page and plug by hand then, as above.

## Run setup

```sh
mix compile --warnings-as-errors
mix brando.setup
```

`brando.setup` composes the operational steps an installed application needs:
asset builds, `ecto.create`/`ecto.migrate`, a superuser account, and default
content seeds. Each step is skipped when its result already exists, so a rerun
after a failure resumes instead of duplicating. Skip steps with `--no-assets`,
`--no-db`, `--no-account` and `--no-seeds`. Setup prompts for anything it needs;
for an unattended run, supply `--email`, `--name` and `--password` for the
account and `--base-url` and `--description` for the seeded site identity. The
account logs in with the password given here; it is not asked to change it on
first login.
`--source PATH` hands a Brando JavaScript source to asset setup. The sections below describe the same
steps as individual tasks, which is what to reach for when you want to control
them separately.

## Build assets

```sh
mix brando.assets.setup
```

Asset setup runs `pnpm install` and `pnpm build` in both consumer asset
directories. It does not build the framework's root asset project. Where the
admin takes BrandoJS from is set in `assets/backend/package.json`, and the
task keeps it:

* **npm**: `"@brandocms/brandojs": "0.55.0"`, Brando's own version. A released
  Brando generates this; `pnpm install` fetches it.
* **A Yalc copy**: `"file:.yalc/@brandocms/brandojs"`, a copy of a Brando
  checkout. A `-dev` Brando generates this, and it is how you work on Brando
  itself. The task publishes the selected Brando dependency's `assets/` to a
  consumer-local Yalc store under `_build` and adds it to the admin. An Elixir
  package from Hex has no JavaScript sources: pass
  `--source /path/to/matching/brando/assets`, or `--npm`.
* **A linked checkout**: `"link:../../brando/assets"` (or a `file:` path
  outside `.yalc`). The task checks that the path holds `@brandocms/brandojs`
  and leaves it to pnpm.

A `package.json` without BrandoJS gets what a generated admin has. To switch,
run `mix brando.assets.setup --local` (or `--source PATH`) to take BrandoJS
from a Yalc copy of a checkout, and `mix brando.assets.setup --npm` to go back
to the npm release of Brando's version. `--npm` also removes the Yalc copy.
The task checks for Node.js, pnpm and, for a Yalc copy, Yalc before it changes
anything.
With a local source, `npx yalc publish` in Brando's `assets` reaches the admin's
running Vite dev server by itself. Its Vite config includes BrandoJS's
`yalcAutoUpdate` plugin, which pulls each publish. Use `--no-build` to install
only.

`pnpm build` writes `admin_manifest.json`, `manifest.json` and assets to the
consumer's `priv/static`. Production uses them, and so does development with
`config :studio, hmr: false`. After framework JS changes, rerun asset setup.

### Vite dev servers

In development the installer sets `config :studio, hmr: true` in
`config/dev.exs`: the admin loads its assets from a Vite dev server for
`assets/backend` on port 3333, and the site from one for `assets/frontend` on
port 3000. The installer adds two endpoint watchers to `config/dev.exs`, so
`mix phx.server` starts both servers and stops them when it stops:

```elixir
config :studio, StudioWeb.Endpoint,
  watchers: [
    vite_admin: {Brando.Vite, :watch, [Path.expand("../assets/backend", __DIR__)]},
    vite_site: {Brando.Vite, :watch, [Path.expand("../assets/frontend", __DIR__)]}
  ]
```

`Brando.Vite.watch/1` runs Vite from the directory's `node_modules`, so run
`mix brando.assets.setup` (or `pnpm install` in both directories) first. Vite's
output goes to the `mix phx.server` log. Vite stops when Phoenix stops, also
when you leave with Ctrl-C.

The installer fills the watchers only when the endpoint has none (phx.new's
`watchers: []`, or no `watchers` key) and `config/dev.exs` does not set
`hmr: false`. Watchers of the application's own are
kept, and the installer prints the two entries to add by hand. Applications
installed by earlier Brando versions have no Vite watchers: add the two entries
above to the endpoint's `watchers` in `config/dev.exs`, or keep running `pnpm dev` in
`assets/backend` and `assets/frontend`.

Both generated `vite.config.js` files set `server.strictPort`, so Vite does
not quietly move to a port Phoenix does not know. When Vite cannot start,
because another process such as another site's Vite server holds its port,
because `node_modules` is missing, or because `node` is not on the `PATH`,
the log has Vite's own output and one error from `Brando.Vite` saying what to
do. Phoenix carries on without that dev server and does not retry it; restart
`mix phx.server` once it is fixed. With a taken port the page loads whatever
answers there, which may be the other site's assets, so give each running site
its own ports (below). When a dev server's scripts fail to load, because it is
not running or cannot compile a module, the admin or the site shows a notice
naming the address it tried. Copy `strictPort` into
the Vite configs of existing applications.

To run two Brando sites at once, give one of them other ports. Export them in
that project's shell environment, for example its `.envrc`, so that Phoenix,
which renders the script tags, and the Vite servers its watchers start read the
same values:

```sh
export BRANDO_VITE_ADMIN_PORT=3334
export BRANDO_VITE_FRONTEND_PORT=3001
```

`BRANDO_VITE_ADMIN_HOST` and `BRANDO_VITE_FRONTEND_HOST` set the hosts
(default `localhost`). To use the built assets instead, run `pnpm build` in
both directories, set `config :studio, hmr: false` in `config/dev.exs` and
remove the two watchers; running `mix brando.install` again leaves them out.

## Initialize and sign in

Review migrations and point the consumer at its intended development database:

```sh
mix ecto.create
mix ecto.migrate
mix brando.gen.languages
mix brando.gen.admin
mix brando.gen.seeds
mix phx.server
```

The language task creates identity/SEO defaults and prints language configuration;
choose English (`en`) for the initial defaults. The admin task prompts for account
details. Open `/admin/login` and sign in with that password; like `brando.setup`'s
account, it is not asked to change it on first login. Account creation and database operations
are separate from the Igniter source plan.

`brando.gen.seeds` creates the content a new site needs before its first request
succeeds: identity and SEO per configured language when missing, seven modules,
a published `index` page built from six of them, a `main` navigation menu and a
`partials/footer` fragment. It owns an account with `--user ID`, defaulting to
the oldest active superuser. `--base-url URL` and `--description TEXT` fill in
a newly created SEO record's base URL and fallback meta description; without a
base URL, canonical links, sharing previews and the sitemap cannot build full
addresses. Existing content of each kind is left untouched,
so the task is safe to rerun; it is a starting point for editing in the admin,
not a migration path. Without it, `/` has no published page and responds 404.
Your application's own `priv/repo/seeds.exs` is preserved and never run for you.

The seeded modules — Hero, Steps, Cards, Tips, Toolbox, Closing and Footer —
double as worked examples of the ref conventions: mono micro-labels and links
live in the module markup, while every piece of copy is a ref an editor can
change. The Toolbox module keeps its task table in markup on purpose, since it
documents the framework rather than the site. Delete the page and the modules
once your own design takes over; nothing else depends on them.

Two conventions the seeds rely on, worth knowing when you write your own:

- A header block's text is inserted raw, so the hero headline carries a
  `<span class="soft">` around its second line to step it back. Newlines in a
  header ref become `<br>`.
- Ref content is parsed for Liquid on its way into the module markup. Copy that
  shows a `{% ref %}` tag — like the Quick start step that explains them — has
  to escape its braces as `&#123;` / `&#125;`, or the renderer consumes it as a
  tag of its own.

For `single`/`multi`, provision the site/environment after public migrations and
initialize content inside that environment as described in the tenancy guide.
Group authorization remains an explicit setup in [Authorization](authorization.md).

## Generate a content type

```sh
mix brando.gen.blueprint Catalog Product
mix compile --warnings-as-errors
mix brando.gen Studio.Catalog.Product
mix brando.gen.blueprint_migration Studio.Catalog.Product
mix ecto.migrate
```

The Blueprint starts with title/slug fields, a listing, a form, and creator,
status and timestamp traits. Review and adapt it before generating storage.
`--plural people` handles irregular names; `--singular` also overrides query names.
The default plural appends `s`. `--interactive` asks for missing domain/schema or
Blueprint arguments. Without it, missing arguments produce actionable errors.

Accept and compile the Blueprint before generating the resource. The resource
command reads compiled metadata, extends its context using AST edits, and adds
admin list/form modules and routes. Multiple resources can share a context.
Existing custom queries remain in place; conflicting functions and owned files
are reported. Add a navigation entry and review the authorization policy explicitly.

<!-- usage-rules:end -->

Public rendering requires an explicit route choice:

```sh
mix brando.gen Studio.Catalog.Product --public-route /products
```

This adds a controller/HTML pair with an index at `/products` and a page per
entry at `/products/:slug`, or `/products/:id` when the Blueprint has no `slug`
field. Pages by id need an integer or UUID primary key named `id`; for another,
the generator stops with an issue. Schemas with a status field expose published
records, and the entry page loads the images its [meta fields](blueprints.md#datasources-metadata-and-json-ld) read, such as
`meta_image`. The entry page
shows the main field and, for a Blueprint with block fields, their rendered
blocks (`Brando.HTML.render_blocks/1`). Templates do not assume an image field.
`--main-field` selects a display/filter field; otherwise the generator prefers
`title`, a string field, then `id`.

With the [CMS public pages](#add-cms-public-pages) (`mix brando.gen.site`, or
`mix brando.install --public-site`), the routes go in a scope that pipes through
`[:browser, :brando_site]`, as the CMS pages do, so tenant, locale, identity,
navigation and [lockdown](#lockdown) apply to them. The scope goes after the
`:brando_site` pipeline and before the CMS catch-all. The controller renders in
`YourWeb.CMS.Layouts` with the `partials` fragments, as `CMS.PageController`
does, and puts the entry's meta tags, title and, for a translatable Blueprint,
hreflang links. A missing entry goes to `BrandoWeb.FallbackController`, which
follows a matching redirect or renders the site's [404 page](#error-pages).

Without the CMS site, the routes pipe through `:browser` only, the pages render
in your application's layout, and the controller resolves the tenant itself. A
missing entry or malformed id raises `Ecto.NoResultsError`, which your
`ErrorHTML` renders as a 404. These pages are not locked by
`Brando.Plug.Lockdown`; the generator's notice says what to wire by hand.
Generate the CMS site before the resource to get the integrated version.

The default Blueprint leaves `absolute_url false`. The notice then prints the
`absolute_url` that matches the new route, such as
`absolute_url ~H"/products/{@entry.slug}"`; set it so admin preview links,
sitemaps and SEO use the page.

For a Blueprint with a `language` field, each language gets its routes, as the
[CMS pages](i18n.md) do: the default language's at `/products`, and every other
language's in a scope under its code, such as `/no/products` (the default
language's too, at `/en/products`, with `scope_default_language_routes: true`).
The languages are read from `config :brando, :languages` and `:default_language`
when the resource is generated. A regional code such as `pt-br` gets the scope
`as: :"pt-br"`, whose helpers (`:"pt-br_product_path"`) `route_i18n` calls. For a
language added later, run the command again: it adds the scopes of the languages
whose routes are missing, and leaves the existing ones.
The pages list and show the request's language with the query's `language:`
option, so translations can share a slug and the context needs no language
clause. With the CMS site, `:brando_site` takes the language from the path;
without it, each scope's `assigns` give it. The notice prints an `absolute_url`
that gives each translation its prefixed URL, for hreflang links, admin previews
and sitemaps: `absolute_url ~H|{route_i18n(@entry, :product_path, :show, [@entry.slug])}|`.
It also prints one when the Blueprint's `absolute_url` gives every language the
same path.

Consumer templates in `priv/templates/brando.gen.blueprint` and
`priv/templates/brando.gen` override package defaults. With a consumer
`controller.ex` or `html.ex` in `priv/templates/brando.gen`, entry pages keep the
`:id` route param, which templates copied before slug routes match, and the
notice says so; the templates' `param` binding then is `"id"`. The Blueprint command also
accepts `--template RELATIVE_PATH`, which takes precedence over the conventional
consumer override. Conflicting output files are preserved for manual integration.

[Blueprint migrations](blueprint_migrations.md) explains snapshot history,
subsequent storage changes, rollback, and explicit rebaseline.

## Framework migrations and upgrades

```sh
mix brando.gen.migrations --dry-run
mix brando.gen.migrations
mix brando.migrate
# For named environments, after public migrations:
mix brando.migrate --tenants
```

The source command adds missing versioned framework migrations, preserves
historical files regardless of their timestamps, and does not recreate the
pre-versioned installation baseline or run the database.

Older installations generated their own `Mix.Tasks.Brando.Upgrade`, which shadows
the library's native upgrade hook. Retire the recognized task in a separate step:

```sh
mix brando.upgrade.prepare
mix compile
```

The plan archives its source under `priv/brando/legacy_tasks` and removes it from
compilation. Customized or unrecognized tasks block removal: rename their module
and task explicitly, preserving your application-specific steps. Compile in a
new invocation before using `mix igniter.upgrade brando`.

Igniter calls the library-owned `brando.upgrade FROM TO` hook. It accepts forward
upgrades from `0.54.0-dev` onward to a 0.54 or 0.55 target, never beyond the
loaded dependency version. Each crossed minor version composes its recipe
before missing framework migrations are planned: a 0.54 → 0.55 upgrade runs
`brando.migrate55` first. A `-dev` version counts as older than every
prerelease and the release of the same version, so a Git or path installation
at `0.55.0-dev` moves onto `0.55.0-beta.0` or `0.55.0` as an upgrade, without a
recipe since both are the 0.55 line. Other versions order as semantic
versions. Equal versions are a no-op; use `brando.gen.migrations` to reconcile
files during development. An application that ran `mix brando.migrate55`
against an earlier `0.55.0-dev` build runs it again after the update to pick up
rewrites added since; the task is idempotent and leaves migrated source unchanged. Applications
with older DSL syntax must first follow [Migrating from 0.53 or 0.54](migrating_from_053.md).
Future release transitions require explicit upgrade recipes and qualification.

## Auxiliary generators

```sh
mix brando.gen.mail
mix brando.gen.sitemap
mix brando.gen.authorization
mix brando.gen.release
mix brando.gen.tenant_migration add_projects
```

All commands use reviewed source plans and consumer namespaces. New dependencies
are fetched once after acceptance. Customized owned files produce conflicts;
consumer templates under `priv/templates/TASK` take precedence. Tenant migration
names use lowercase letters, digits and underscores; `--interactive` guides a
missing name. Existing migration implementations and timestamps are preserved. New Blueprint
storage uses tenant migrations in single/multi mode; run `mix brando.migrate --tenants`
after public migrations. History in a different directory requires an explicit
transition decision.

Mail generation reuses a Phoenix mailer or creates `MyApp.Mailer`, and
supplies local/test adapter defaults plus a default Req API client; Swoosh and
Req come with Brando, so no dependency is added. It also points Brando at the
mailer, for the email Brando sends itself, and writes a placeholder sender
(`noreply@example.com`) to replace; see [Email](email.md).
`mix brando.gen.mail --contact` also scaffolds a contact form,
`MyApp.Contact.ContactForm`; build its notifications with
`MyApp.Emails.contact(changeset, from: ..., to: ...)`.
Invalid form data raises before constructing an email. Configure the production
adapter and credentials deliberately; generating mail helpers never sends mail.

The sitemap selects published pages; review their public URL rules before calling
`Brando.Sitemap.generate_sitemap/0`. Authorization generation starts from the
maintained default policy; review permissions for your application content types.

Release generation creates `MyApp.ReleaseTasks` and adds a missing Mix release
definition, with `steps: [:assemble, :tar]` for Florist. `brando.install` does
the same, so run it only for an application installed before that. It
preserves existing release settings, runtime configuration, secrets,
Dockerfiles and deployment files, with a notice when an existing release
writes no tarball, or when `mix.exs` defines releases but none named after the
application (it adds no second release then). Build with `MIX_ENV=prod mix release`,
then invoke migrations explicitly as described in [Deployment](deployment.md).
`brando.install.fabfile` is retired and directs callers to release generation and
Florist; it does not modify existing Fabric files. `brando.install` no longer
writes `fabfile.py` or `deployment.cfg` into a new application.

```sh
mix brando.gen.otel
mix brando.gen.otel --adapter bandit --exporter otlp
```

Telemetry infers a single declared Bandit/PlugCowboy dependency or asks for an
explicit `--adapter`. It uses the discovered service namespace and the Repo's
configured event prefix, preserves existing configuration, and guards against
legacy duplicate instrumentation. [Phoenix instrumentation](https://hexdocs.pm/opentelemetry_phoenix/OpentelemetryPhoenix.html)
already covers LiveView. The [OpenTelemetry SDK](https://hexdocs.pm/opentelemetry/readme.html)
supports the default `traces_exporter: :none`; opt into OTLP and set the standard
`OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_EXPORTER_OTLP_HEADERS` environment variables.
Existing exporter choices remain unchanged on reruns.

`brando.setup.tenancy` also accepts `--interactive` for missing mode/site choices.
Without it, pass the options explicitly; `--yes` only accepts the diff.
