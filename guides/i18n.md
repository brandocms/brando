# Languages and translations

Brando separates three things: the language of stored content, the administrator's
interface language, and Gettext translations of application strings. Adding a
language to the picker does not translate existing pages or create public routes.

This walkthrough adds Norwegian to an English consumer. It assumes public
migrations have run and `MyAppWeb.Gettext` and `MyAppAdmin.Gettext` exist.

<!-- usage-rules:start topic="i18n" -->

## Configure content and interface languages

In `config/brando.exs`:

```elixir
config :brando,
  default_language: "en",
  languages: [
    [value: "en", text: "English"],
    [value: "no", text: "Norsk"]
  ],
  default_admin_language: "en",
  admin_languages: [
    [value: "en", text: "English"],
    [value: "no", text: "Norsk"]
  ],
  scope_default_language_routes: false
```

Check `config/runtime.exs` as well: the installer reads
`BRANDO_DEFAULT_LANGUAGE` there and sets an admin default. Runtime configuration
wins over the earlier file. Set the environment variable consistently and restart
after changing language configuration; the language field is compiled from the
configured choices.

<!-- usage-rules:end -->

Create identity and SEO defaults for the new language with the interactive
`mix brando.gen.languages` task, then apply the configuration it prints. It creates
records and prints instructions; it does not rewrite your config or translate
content. In tenant installations, create the records in the intended environment
instead of assuming a command without tenant context reaches it. See
[Identity and SEO](identity_and_seo.md) for the context APIs.

The user's `language` selects the admin interface. The admin locale plug sets
both `Brando.Gettext` and the consumer's admin Gettext backend. It does not
change the language of the entry being edited.

## Translate a page

In the page listing, open the English page's menu and choose
**Duplicate to [NO]**. Brando copies the page, its content and metadata into a
Norwegian page, links the two as language versions (alternates), and opens the
copy. Give it its own URI (`om`) and title, translate the text, and publish.

With an AI model configured, **Translate to [NO]** does the same and has the
model translate the copy's text for you to review. Both actions appear on every
entry of a translatable schema whose context can duplicate it, when the site has
more than one language. For a schema in synchronized mode, use **Create a
translation** in the editor instead (see [Synchronized translations](#synchronized-translations)).

To link two pages that already exist, open the editor's **Languages** button and
choose **Select entries to link**. From code, the same relationship is:

```elixir
alias Brando.Pages
alias Brando.Pages.Page

{:ok, english} = Pages.get_page(%{matches: %{uri: "about", language: "en"}})
{:ok, norwegian} = Pages.get_page(%{matches: %{uri: "om", language: "no"}})
:ok = Page.Alternate.add(english.id, norwegian.id)

{:ok, english} = Pages.get_page(%{
  matches: %{id: english.id},
  preload: [:alternate_entries]
})
```

Call `add/2` once for a pair; it inserts both directions. `Page.Alternate.delete/2`
removes both directions and evicts both query-cache entries. Linking itself
copies no content. In a synchronized group (see below), adding an alternate
re-syncs the translations whose links were waiting for that entry. Custom
Blueprints opt in through `trait :translatable`; `alternates: false` keeps the language field without these
relationships. Menus and fragments use that latter form: match their keys across
languages explicitly.

### Synchronized translations

`trait :translatable, mode: :synchronized` lets one language version of an
entry, its source, control the structure of the others:

```elixir
trait :translatable,
  mode: :synchronized,
  source_controlled_fields: [
    :project_year,
    {:module, "hero-banner", [:layout]},
    credits: [:url]
  ]
```

Saving the source computes a pending version for each translation: block and
subform-row membership, order and nesting, media, and the source-controlled
values follow the source; titles, block text, captions and alt text keep their
translations. New text is marked for translation and changed source text for
review. The published translation does not change until it is saved.

Links to other content (block identifiers and identifier variables, such as a
project tile's link to a case) follow the source too, pointed at the same
content's version in the translation's language. Swap the case a tile links to
in the source, and the translation's tile follows to that case's version in its
own language. When that version does not exist yet, the link keeps pointing at
the source-language content, so it still works, and is marked as awaiting
translation. Creating that translation later re-syncs the waiting pages, and
the link moves to it.

Link pickers in the editor offer content in the entry's own language, so a
Norwegian page links Norwegian cases and its English translation English ones.

A link variable with a typed URL is different: a URL is often language-specific
(a `/no/` path, a localized external site), so it is kept per language like
text. A new URL link starts from the source's URL, marked for translation; a
changed URL in the source is marked for review and the translation keeps its
own until an editor updates it. Whether a link points at an entry or a URL
follows the source: switching a tile from one to the other switches the
translation's too, starting from the source's value.

The mode defaults to `:independent`, the behaviour of a plain
`trait :translatable`. Synchronized mode needs framework migration **182**
(`brando_182_add_synchronized_translations`). It adds a `sync_uid` to blocks
and table rows, pairing each with its counterpart in the other language
versions, and creates the `translation_groups`,
`translation_group_members`, `translation_pending_versions` and
`translation_work_items` tables. They live beside the entries, in the
current schema. Pending versions are computed by
`Brando.Worker.TranslationSync` on Oban's `default` queue, so a translation's
work appears shortly after the source is saved, not in the same request.
Every save queues it: the admin form, the context's `create_*` and `update_*`
functions, revision restores, proposals and content transfer. A saved
translation queues the recompute of its own pending version the same way.
Code that writes an entry with `Repo` directly calls
`Brando.Translations.source_saved/2` itself.

Brando's own `Brando.Pages.Page` uses independent mode unless the site
configures it (see [Synchronized pages](#synchronized-pages)).

#### What follows the source

Every value of a synchronized entry falls in one of four classes. Only the
fourth needs configuring:

| Class | What | On a source save |
| --- | --- | --- |
| Structure | Which blocks exist, their order and nesting, and each block's module, palette, container, datasource and active flag; the refs and variables of each block; table rows; subform rows (matched by `uid`) | The translation follows the source |
| Media and links | Asset fields (`:image`, `:file`, `:video`, `:gallery`); images, videos and files in refs and variables; a gallery's media and their order; links to other content (block identifiers, identifier variables) and a relation to the schema itself (a page's parent), pointed at the same content in the translation's language | The translation follows the source |
| Text | Attributes edited with a `:text`, `:textarea` or `:rich_text` input; `meta_title` and `meta_description`; the text of text, HTML, header and Markdown refs; a picture's title, credits and alt text; a video's title; per-item gallery texts; `:string`, `:text` and `:html` variables; a link variable's text and typed URL; subform fields with a text input | Kept; new text is marked **translate**, changed source text **review** |
| Everything else | Other attributes (numbers, booleans, dates, selects, slugs), `belongs_to` relations, other variable values (booleans, selects, colors, dates), the data of other refs (a map or embed, for example), subform fields without a text input | Copied when the translation is created, then each language's own |

`id`, `language`, `status`, `publish_at`, timestamps, `creator_id`,
`updated_by_id` and `sequence` are never synchronized. A translation keeps its
own gallery record; only the gallery's contents follow the source.

`source_controlled_fields` moves values from the last class into "follows the
source": use it for facts that are the same in every language.
`language_controlled_fields` moves assets the other way (see
[Language-controlled assets](#language-controlled-assets)).

#### Source-controlled values

A project's year, client site and category are the same in every language, as
are each credit's link and role and the layout of its hero module. Only the
credit's caption and the texts are translated:

```elixir
trait :translatable,
  mode: :synchronized,
  source_controlled_fields: [
    :year,
    :client_url,
    :category,
    credits: [:url, :role],
    {:module, "hero-banner", [:layout, :dark]}
  ]
```

- `:year` and `:client_url` are attributes, `:category` a `belongs_to`
  relation. Without the selector, each language could set its own year after
  the translation was created. Now a source save carries the source's year to
  every translation's pending version.
- `credits: [:url, :role]` addresses fields of an owned subform. It needs a
  `has_many ..., cast: true` (or `embeds_many`) whose schema has
  `trait :ensure_uid`, with `url` and `role` as inputs of the subform:

  ```elixir
  relations do
    relation :credits, :has_many, module: MyApp.Projects.Credit, cast: true
  end
  ```

  Rows are added, removed and reordered with the source in any case; the
  selector decides which of a row's values follow it. `caption`, a `:text`
  input, stays translated; a field neither listed nor text is copied once.
- `{:module, "hero-banner", [:layout, :dark]}` makes two variables of the
  module with uid `"hero-banner"` follow the source, in every block built from
  that module. A `:layout` variable on another module stays each language's
  own. Keys may be atoms or strings.

When a translation holds a different value for a source-controlled field, its
pending version sets the source's value and lists it as a **shared update** for
the editor to accept.

##### Selector reference

`source_controlled_fields` takes three kinds of selector:

- **Top-level attributes, assets and `belongs_to` relations**, as plain names.
  Assets always follow the source; listing them documents it.
- **Fields of an owned subform**, as `subform: [fields]`. The subform must be a
  `has_many` with `cast: true`, or an `embeds_many`, whose rows are matched by a
  `uid` attribute (`trait :ensure_uid`); the fields must be inputs of that
  subform in the form. `id`, `uid`, `sequence`, timestamps and foreign keys
  identify rows and are refused. Other fields of the row stay the
  translation's own.
- **Variables of one block module**, as `{:module, "uid", [keys]}`, where `uid`
  is the module's `uid` (the identifier `Brando.Content.Definition` uses). The
  same variable key on another module stays language-specific. Modules are
  content, so these are checked at runtime: `Brando.Translations.check_config/1`
  lists a module uid or variable that does not exist, for example after a
  module was renamed or its variable removed. Until the selector is fixed, such
  a variable is simply not source-controlled.

Selectors are validated when the Blueprint compiles; an unknown field, a
non-owned relation or an identity field raises. So does listing the same
subform or module twice, `source_controlled_fields` without
`mode: :synchronized`, and `mode: :synchronized` with `alternates: false`.
Variables of table rows and of nested subforms cannot be addressed, and a
subform whose rows have no `uid` is not synchronized.

#### Language-controlled assets

Assets follow the source by default. When one should differ per language — a
listing image with text in it, a document in each language — list it in
`language_controlled_fields`:

```elixir
trait :translatable,
  mode: :synchronized,
  source_controlled_fields: [:year],
  language_controlled_fields: [:listing_image, :brochure]
```

The asset is copied when a translation is created, then each language keeps its
own: a source save doesn't change it, and it stays editable in the translation's
form. `:image`, `:file`, `:video` and `:gallery` assets can be listed, and a
relation to the schema itself, such as a page's `:parent`, for a hierarchy that
differs per language. Everything else is already each language's own unless it
is source-controlled.
Listing a field in both options, or using the option without
`mode: :synchronized`, raises when the Blueprint compiles. Media inside blocks
always follow the source.

#### Synchronized pages

Pages are independent by default. To synchronize them, configure Brando's Page:

```elixir
config :brando, Brando.Pages.Page,
  translatable: [
    mode: :synchronized,
    source_controlled_fields: [:template, :is_homepage, :has_url, :css_classes]
  ]
```

The `translatable` keyword takes the same options as the trait. The fields
above are a sensible start: the template and page flags are the same in every
language, while `uri`, `title` and the meta fields stay translated. Run
migration 182 first.

The config is read at runtime; no recompile is needed. In a tenant
installation, `translatable_sites` sets it per site key and replaces
`translatable` for that site:

```elixir
config :brando, Brando.Pages.Page,
  translatable: [mode: :independent],
  translatable_sites: %{"acme" => [mode: :synchronized, source_controlled_fields: [:template]]}
```

Brando validates these at boot like a Blueprint's own options and refuses to
start on an invalid one. Other Blueprints configure translation in their own
code; only a Blueprint that declares `trait :translatable, runtime_config: true`
reads this config.

A page's parent follows the source, pointed at the parent's version in the
translation's language. When the parent has no version in that language yet,
the translation keeps its own parent and shows the parent as awaiting
translation; creating the parent's translation fills it in. For a hierarchy
that differs per language, list `:parent` in `language_controlled_fields`.
Fragments are separate entries and are not part of a page's synchronization.

#### Adding synchronized mode to an existing Blueprint

1. Make sure framework migration 182 has run: `mix brando.gen.migrations`,
   then `mix brando.migrate` (and `--tenants` for named environments).
   Synchronized mode adds no columns to your own tables — `language` and the
   alternates relation come from `trait :translatable` — so no Blueprint
   migration is needed.
2. If the schema was not translatable before, adding the trait adds both: run
   `mix brando.gen.blueprint_migration` for it. The generated migration leaves
   `language` empty on existing rows, and it is required, so add a backfill to
   it before running it, for example
   `execute "UPDATE projects SET language = 'no' WHERE language IS NULL"`.
3. Translations start as a copy of the source, so the context needs a
   duplicate mutation (`mutation :duplicate, {Project, change_fields: [...]}`).
   Without one, **Create a translation** isn't offered.
4. A source-controlled `slug` is the same in every language, so its uniqueness
   must be per language: `unique: [prevent_collision: :language]`, and a
   Blueprint migration for the index.
5. Run `mix brando.identifiers.sync`, so identifiers made before the schema
   was translatable get their entry's language. Link pickers filter on it.
6. Add `mode: :synchronized` and any `source_controlled_fields`, and deploy.
   Call `Brando.Translations.check_config(MyApp.Projects.Project)` against the
   target database: it returns `[]`, or the module uids and variables in your
   selectors that do not exist there.
7. Nothing changes for existing entries until an editor acts. An entry joins a
   group when it gets its first translation through **Create a translation**,
   and becomes that group's source.

Translations that already exist, linked as alternates, stay independent. They
are not joined to the group and not offered under **Create a translation**,
and there is no way to adopt one: its blocks were copied on their own and have
their own sync identities, so the sync could not pair them with the source's.
To synchronize such a pair, create the translation with **Create a
translation**, move the text over from the old version, publish it, and delete
the old one. Or leave it independent; both kinds can live in one schema.

From code, `create_target/4` returns `{:error, :language_exists}` for a
language the group already has or that an independent version holds. Deleting
the old version frees its language.

#### In the admin

- **Creating a translation.** An entry of a synchronized schema lists the
  languages it has no version in. Creating one makes an unpublished copy,
  linked as an alternate, and the entry becomes the source. The copy starts
  from the source's text (the context's duplicate marks copies, a translation
  doesn't), and entries a duplicate would copy along, such as a page's child
  pages and fragments, are left out: each is translated on its own. Languages
  that already have an independent alternate are not offered; joining existing
  alternates to a group is not supported.
- **Editing a translation.** Opening a translation loads its pending version
  into the form as unsaved changes and lists the work: text to translate, text
  to review, values updated from the source, links waiting for a translation,
  and structural changes with no text work. Link items name the entry they now
  point at or wait for. A pending version computed before the translation last
  changed (a published revision, a scheduled release) is recomputed first, so
  applying it never overwrites that change. The affected blocks and fields are
  marked. Mark text as **Reviewed** when it needs no change. Saving writes the
  pending version and resolves only the work of the version the editor loaded;
  what was not done stays open. A published translation updates on save; a new
  one stays a draft until it is published.
- **What a translation cannot change.** Structure, media and source-controlled
  values follow the source. Their controls are hidden or disabled in a
  translation, and the save refuses any change to them, whatever sent it.
- **Source changes during editing.** If the source is saved again while a
  translation is open, the save still writes what the editor reviewed, then
  loads the newer changes into the form and says so. Newer work stays open.
- **Minor corrections.** On the source, **Save minor text corrections** saves
  without asking the translations to review changed text. Structure, shared
  values and new text are still synchronized, and work already open stays.
- **Make independent** stops a translation from following its source. It keeps
  its content, its unsaved changes and its alternate link. **Make source**
  hands the source role to a translation; the others follow it from its next
  save. Neither publishes anything. The source itself cannot be made
  independent; make another version the source first.
- **Deleting a source** is refused while it has synchronized translations
  (`{:error, :group_has_synchronized_members}` from the delete mutation).
  Make them independent, or hand the source role on, first.
- **Listings** show each language version of a synchronized entry with its open
  work — to translate, to review, links waiting, or updated from the source —
  linking to that version. Only versions the user may read are listed.

#### From code

`Brando.Translations` is the API the admin uses:

```elixir
alias Brando.Translations

{:ok, norwegian} = Translations.create_target(Project, english.id, "no", user)
{:ok, _member} = Translations.make_independent(Project, norwegian.id, user)
{:ok, _member} = Translations.transfer_source(Project, norwegian.id, user)

# %{entry_id => [%{language: "no", entry_id: 8, role: :target, ...}]}
Translations.listing_status(Project, entries, user)
```

`create_target/4` duplicates the source through the context's `duplicate_*`
mutation as an unpublished draft that keeps each block's `sync_uid`, links it
as an alternate and computes its first pending version. It refuses a language
the group already has. `make_independent/3` returns `{:error, :is_source}` for
the source; `transfer_source/3` takes only a synchronized translation.

Duplication itself was changed for this and affects every duplicate and
translate action. Galleries on gallery assets, refs and vars are cloned, so the
copy no longer shares the original's gallery. Owned `has_many` rows (subforms
with `cast: true`) are copied with the same `uid`; linking rows such as
alternates are dropped instead of being moved to the copy. `change_fields`
passed as override options to a `duplicate_*` mutation normally replace the
context's own; with `merge_change_fields: true` the context's handlers are kept
for every field the override does not name.

## Single-language sites

<!-- usage-rules:start topic="i18n" -->

When `:languages` has one entry, the admin hides the language select on pages,
fragments, menus and global sets, and the sidebar's content-language switch.
New entries still get the editor's content language. Hide the language input
of your own Blueprints the same way:

```elixir
input :language, :select,
  options: :languages,
  hidden: &Brando.I18n.SingleLanguage.single_language?/1
```

Capture it from `Brando.I18n.SingleLanguage`, not `Brando.I18n` (which
delegates to it). A capture in a Blueprint is a compile-time reference, and
`Brando.I18n` reaches back into `Brando`, which puts every Blueprint that
captures it in a compile-connected cycle. `SingleLanguage` only reads the
application environment.

<!-- usage-rules:end -->

## Translated strings in one field

Short texts that belong to one record but differ per language, such as an
image's alt text, use the `:i18n_string` attribute type: a jsonb map of
language → text. Edit it with the `:i18n_text` or `:i18n_textarea` input,
which shows one tab per language:

```elixir
attribute :caption, :i18n_string

input :caption, :i18n_text, label: t("Caption"), languages: :content
```

The tabs list the admin languages unless `languages: :content` selects the
site's content languages; use `:content` for text shown on the site. A
language's tab is marked, in amber, only while another language has text, so
an empty optional field shows no marks. Blank values are stored as `nil`.

Read one language with `Brando.Type.I18nString.get(value, language)`. It
returns that language's text, else the default content language's, else
`nil`. A plain string, from older data or a form that sent one value, casts
under the default content language. In Liquid, use the `i18n` filter; see
[Images, files, and galleries](media.md#render-responsive-images) for image
texts.

## Route the requested language

The generated `put_locale` plug uses `Brando.I18n.parse_path/1`. With the config
above, `/` becomes `{ "en", ["index"] }`, `/about` becomes
`{ "en", ["about"] }`, and `/no/om` becomes `{ "no", ["om"] }`.
An unknown first segment remains part of the path in the default language; it is
not accepted as a new language code. Page controllers must include the language
in the query, as shown in [Pages](pages.md#resolve-and-render-public-pages).

<!-- usage-rules:start topic="i18n" -->

For application-specific routes, declare both paths before `page_routes()`:

```elixir
scope "/", assigns: %{language: "en"} do
  pipe_through :browser
  get "/news", MyAppWeb.PostController, :index

  scope "/no", as: :no, assigns: %{language: "no"} do
    get "/nyheter", MyAppWeb.PostController, :index
  end

  page_routes()
end
```

Use `conn.assigns.language` in the controller's content filter. In HEEx:

```heex
<a href={Brando.I18n.Helpers.localized_path(@language, :post_path, [@conn, :index])}>
  {gettext("News")}
</a>
```

`localized_path/3` selects the localized router helper when present. If it is
absent at the requested arity, it falls back to the unscoped helper. If neither
exists, it returns `"/<url cannot be localized>"`; treat that as a routing error.
For catch-all pages, use `Brando.Blueprint.URL.resolve(page)` so the page's URL
rules handle language prefixes. A generic `page_path` helper alone does not
translate the URI or prepend a locale to its path list.

<!-- usage-rules:end -->

If English should live under `/en`, set `scope_default_language_routes: true`
and give custom English routes an `as: :en` scope too. Host-based language
selection is available through `plug :put_locale, by_host: %{"example.no" => "no"}`;
keep tenant/domain resolution and controller path handling consistent with that
choice.

## Emit language alternatives

Preload `:alternate_entries`, call `Brando.Plug.HTML.put_hreflang(conn, page)` in
the controller, and place this in the HTML head:

```heex
<Brando.HTML.render_hreflangs conn={@conn} />
```

It emits canonical and alternate URLs from the entry URL definitions. Inspect
the generated URLs rather than constructing translations by swapping a prefix:
`/about` and `/no/om` have different slugs. Do not link unpublished translations
from your own language switcher; filter its candidates for public eligibility.

## Translate interface strings with Gettext

Backend modules use `Gettext.Backend`; callers use `Gettext` with that backend:

```elixir
defmodule MyAppWeb.Gettext do
  use Gettext.Backend, otp_app: :my_app, priv: "priv/gettext/frontend"
end

# In a controller or component that uses translated strings:
# use Gettext, backend: MyAppWeb.Gettext
```

Extract literal strings, then merge each consumer catalogue:

```bash
mix gettext.extract
mix gettext.merge priv/gettext/frontend --locale no
mix gettext.merge priv/gettext/backend --locale no
```

Translate the generated `.po` files and recompile. Frontend and admin catalogues
are separate; editing the frontend catalogue will not translate admin labels.
See [Migrating from 0.53 or 0.54](migrating_from_053.md) for upgrading older Gettext callers.

<!-- usage-rules:end -->

Finally, visit both language routes, reopen both pages, and inspect their menu,
identity, metadata, and alternate links. Also request a missing Norwegian page:
it should use your missing-page behavior, not silently serve English content.
