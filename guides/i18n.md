# Languages and translations

Brando separates three things: the language of stored content, the administrator's
interface language, and Gettext translations of application strings. Adding a
language to the picker does not translate existing pages or create public routes.

This walkthrough adds Norwegian to an English consumer. It assumes public
migrations have run and `MyAppWeb.Gettext` and `MyAppAdmin.Gettext` exist.

<!-- usage-rules:start topic="i18n" -->

## Configure content and interface languages

In `config/brando.exs`:

```elixir
config :brando,
  default_language: "en",
  languages: [
    [value: "en", text: "English"],
    [value: "no", text: "Norsk"]
  ],
  default_admin_language: "en",
  admin_languages: [
    [value: "en", text: "English"],
    [value: "no", text: "Norsk"]
  ],
  scope_default_language_routes: false
```

`languages` and `admin_languages` are compile-time configuration: a `language`
field accepts the codes configured when Brando and the Blueprint were compiled.
Set them in `config/brando.exs` or `config/config.exs`, not in
`config/runtime.exs`, which is read after compilation. To add a language, add
it to the list and restart. Mix sees the changed value and recompiles Brando,
and the Blueprints with a `language` field, before the application starts; for
Brando from Hex or Git that is a full compile of Brando.

A release whose `config/runtime.exs` sets either list to anything other than
the compiled value (labels and order included, and a list compile-time config
leaves unset) stops at boot with Elixir's message naming `:brando` and the
key. Under Mix, `Brando.System.initialize/0`
stops boot when the codes differ from the compiled ones, names the key and the
codes, and gives the command to run, `mix deps.compile brando --force`.

`default_language` is read while the application runs, so `config/runtime.exs`
may set it, from an environment variable such as `BRANDO_DEFAULT_LANGUAGE`. A
new user's content language starts as the `default_language` configured when
the user is created.

On a multi-site installation this list is what the installation can hold, and
each site uses its own subset with its own default language. See
[Languages per site](tenancy_and_environments.md#languages-per-site).

<!-- usage-rules:end -->

Create identity and SEO defaults for the new language with the interactive
`mix brando.gen.languages` task, then apply the configuration it prints. It creates
records and prints instructions; it does not rewrite your config or translate
content. In tenant installations, create the records in the intended environment
instead of assuming a command without tenant context reaches it. See
[Identity and SEO](identity_and_seo.md) for the context APIs.

The user's `language` selects the admin interface. The admin locale plug sets
both `Brando.Gettext` and the consumer's admin Gettext backend. It does not
change the language of the entry being edited.

## Translate a page

In the page listing, open the English page's menu and choose
**Duplicate to [NO]**. Brando copies the page, its content and metadata into a
Norwegian page, links the two as language versions (alternates), and opens the
copy. Give it its own URI (`om`) and title, translate the text, and publish.

With an AI model configured, **Translate to [NO]** does the same and has the
model translate the copy's text for you to review. Both actions appear on every
entry of a translatable schema whose context can duplicate it, when the site has
more than one language. For a schema in synchronized mode, use **Create a
translation** in the editor instead (see [Synchronized translations](#synchronized-translations)).

In an entry's editor, the content language switch at the foot of the sidebar
shows the entry's language. Choose another language there to open the entry's
version in it, when you may read one; your content language changes with it, so
the listing you return to is in that language. A language without a version says
so, or, on a synchronized schema, offers **Create translation**, which sets your
content language to the new translation's; one whose version is in the trash
says that instead, and one whose versions you may not read says **No access**. Leaving an editor this way warns
about edits that have not reached recovery storage yet, as any link out of it
does. On a schema without languages, and on every other screen, the switch
changes your content language only.

An entry's language versions are one set, the same from every version in it:
the entries linked to it, the entries linked to those, and so on, and on a
synchronized schema the members of its translation group. With an English and a
German page each linked to the Norwegian one, the English page's switch opens
the German page, and a German version is not created beside it. Where the set
holds two versions in one language, the switch opens one outside the trash
before one in it, then one linked to the entry before one linked through
another version.

To link two pages that already exist, open the editor's **Languages** button and
choose **Select entries to link**. The drawer lists every version in the set
the editor may read; one linked through another version says which language it
is linked through, and is unlinked from that version, not here. From code, the same relationship is:

```elixir
alias Brando.Pages
alias Brando.Pages.Page

{:ok, english} = Pages.get_page(%{matches: %{uri: "about", language: "en"}})
{:ok, norwegian} = Pages.get_page(%{matches: %{uri: "om", language: "no"}})
:ok = Page.Alternate.add(english.id, norwegian.id, current_user)

{:ok, english} = Pages.get_page(%{
  matches: %{id: english.id},
  preload: [:alternate_entries]
})
```

Call `add/3` once for a pair; it inserts both directions. `Page.Alternate.delete/3`
removes both directions and evicts both query-cache entries. The last argument
is the user acting: with group authorization they need `update` on both
entries, and `{:error, :forbidden}` comes back otherwise. Leave it out (it
defaults to `:system`) only in trusted code, such as a seed or a migration. Linking itself
copies no content. In a synchronized group (see below), adding an alternate
re-syncs the translations whose links were waiting for that entry. Custom
Blueprints opt in through `trait :translatable`; `alternates: false` keeps the language field without these
relationships. Menus use that latter form: match their keys across languages
explicitly.

Fragments have language links too, but a template finds a fragment by its keys
and language, not by its links: `{% fragment "footer" "contact" %}` prints the
fragment with those keys in the page's language whether or not it is linked.
The fragment form's **Languages** drawer lists the fragment's linked versions,
and below them the fragments with its keys in other languages that are not
linked, each with a button that links it. Both lists show only the fragments
the editor may read; a click opens one.

A Blueprint whose language versions share some values names them with
`matched_by`, as Brando's fragment does with its keys:

```elixir
trait :translatable, matched_by: [:parent_key, :key]
```

An entry with those values in another language is then one of its versions,
linked or not: the drawer lists it, and no translation is created beside it.
In synchronized mode the values are source-controlled.

To link the fragments that already exist with the same keys in different
languages, run `mix brando.fragments.pair`. It changes nothing, and lists the
keys it would link and the ones it cannot: a key two fragments hold in one
language, and a key whose fragment is already linked to a fragment with other
keys (or one in the trash) are left for an editor to sort out in the drawer. A
key held in one language only has nothing to link. Fragments in the trash are
left out. Then run it with `--apply`: each key's links are written in one
transaction, after the key is checked again, so a fragment renamed, trashed or
linked by an editor since is reported and left as it is, and a link left one
way is completed. Run it again at any time; linked keys stay as they are, and
the pages that embed their fragments are synchronized again, in case an
earlier run stopped before it got that far. In a
tenant installation, name the environment with `--site KEY --environment KEY`:
the list and the links are that environment's. Linking copies no content, and a
linked fragment stays independent.

### Synchronized translations

`trait :translatable, mode: :synchronized` lets one language version of an
entry, its source, control the structure of the others:

```elixir
trait :translatable,
  mode: :synchronized,
  source_controlled_fields: [
    :project_year,
    {:module, "hero-banner", [:layout]},
    credits: [:url]
  ]
```

Saving the source computes a pending version for each translation: block and
subform-row membership, order and nesting, media, and the source-controlled
values follow the source; titles, block text, captions and alt text keep their
translations. New text is marked for translation and changed source text for
review. A review item keeps the source's text from before the change: the
text the translation was last synchronized against. When the source changes
the text again before the review is done, the item keeps that first text,
the one the translation was written from. Each translation keeps the source's
texts of its last synchronization for this, beside their digests: about as
much again as the source's text, per language version. Review items raised
before `brando_239`, and the first ones after it for a translation not
synchronized since, have no previous text. Neither has a review still open
when another language version becomes the source, nor one saved from a
version the source has since changed: the source's text that version was
read against is not kept. The published translation does not change until
it is saved.

Links to other content (block identifiers and identifier variables, such as a
project tile's link to a case) follow the source too, pointed at the same
content's version in the translation's language. Swap the case a tile links to
in the source, and the translation's tile follows to that case's version in its
own language. When that version does not exist yet, the link keeps pointing at
the source-language content, so it still works, and is marked as awaiting
translation. Creating that translation later re-syncs the waiting pages, and
the link moves to it.

Link pickers in the editor offer content in the entry's own language, so a
Norwegian page links Norwegian cases and its English translation English ones.

A link variable with a typed URL is different: a URL is often language-specific
(a `/no/` path, a localized external site), so it is kept per language like
text. A new URL link starts from the source's URL, marked for translation; a
changed URL in the source is marked for review and the translation keeps its
own until an editor updates it. Whether a link points at an entry or a URL
follows the source: switching a tile from one to the other switches the
translation's too, starting from the source's value.

The mode defaults to `:independent`, the behaviour of a plain
`trait :translatable`. Synchronized mode needs framework migration **182**
(`brando_182_add_synchronized_translations`). It adds a `sync_uid` to blocks
and table rows, pairing each with its counterpart in the other language
versions, and creates the `translation_groups`,
`translation_group_members`, `translation_pending_versions` and
`translation_work_items` tables. They live beside the entries, in the
current schema. Pending versions are computed by
`Brando.Worker.TranslationSync` on Oban's `default` queue, so a translation's
work appears shortly after the source is saved, not in the same request.
Every save queues it: the admin form, the context's `create_*` and `update_*`
functions, revision restores, proposals and content transfer. A saved
translation queues the recompute of its own pending version the same way.
Code that writes an entry with `Repo` directly calls
`Brando.Translations.source_saved/2` itself.

Brando's own `Brando.Pages.Page` uses independent mode unless the site
configures it (see [Synchronized pages](#synchronized-pages)).

#### What follows the source

Every value of a synchronized entry falls in one of four classes. Only the
fourth needs configuring:

| Class | What | On a source save |
| --- | --- | --- |
| Structure | Which blocks exist, their order and nesting, and each block's module, palette, container, datasource and active flag; the refs and variables of each block; table rows; subform rows (matched by `uid`) | The translation follows the source |
| Media and links | Asset fields (`:image`, `:file`, `:video`, `:gallery`); images, videos and files in refs and variables; a gallery's media and their order; links to other content (block identifiers, identifier variables), the fragment a fragment block embeds, a `belongs_to` relation to the schema itself (a page's parent), and a synchronized fragment's page, pointed at the same content in the translation's language | The translation follows the source |
| Text | Attributes edited with a `:text`, `:textarea` or `:rich_text` input; `meta_title` and `meta_description`; the text of text, header and Markdown refs; the values of an HTML ref's `text` parameters; a picture's title, credits and alt text; a video's title; per-item gallery texts; `:string`, `:text` and `:rich_text` variables; a link variable's text and typed URL; subform fields with a text input | Kept; new text is marked **translate**, changed source text **review** |
| Everything else | Other attributes (numbers, booleans, dates, selects, slugs), other `belongs_to` relations, other variable values (booleans, selects, colors, dates), the data of other refs (a map or embed, for example), subform fields without a text input | Copied when the translation is created, then each language's own |

`id`, `language`, `status`, `publish_at`, timestamps, `creator_id`,
`updated_by_id` and `sequence` are never synchronized. A translation keeps its
own gallery record for a gallery asset and a gallery ref, a ref the source
adds later included: the translation's save gives it a copy of the source's
gallery. Only the gallery's contents follow the source. A gallery variable
shows the source's gallery record itself until the translation is made
independent.

`source_controlled_fields` moves values from the last class into "follows the
source": use it for facts that are the same in every language.
`language_controlled_fields` moves assets the other way (see
[Language-controlled assets](#language-controlled-assets)).

#### Source-controlled values

A project's year, client site and category are the same in every language, as
are each credit's link and role and the layout of its hero module. Only the
credit's caption and the texts are translated:

```elixir
trait :translatable,
  mode: :synchronized,
  source_controlled_fields: [
    :year,
    :client_url,
    :category,
    {:module, "hero-banner", [:layout, :dark]},
    credits: [:url, :role]
  ]
```

- `:year` and `:client_url` are attributes, `:category` a `belongs_to`
  relation. Without the selector, each language could set its own year after
  the translation was created. With it, a source save carries the source's year
  to every translation's pending version. The relation is copied as it is,
  even when categories have language links: every translation points at the
  source's category.
- `credits: [:url, :role]` addresses fields of an owned subform. It needs a
  `has_many ..., cast: true` (or `embeds_many`) whose schema has
  `trait :ensure_uid`, with `url` and `role` as inputs of the subform:

  ```elixir
  relations do
    relation :credits, :has_many,
      module: MyApp.Projects.Credit,
      cast: true,
      sort_param: :sort_credits_ids,
      drop_param: :drop_credits_ids
  end
  ```

  Rows are added, removed and reordered with the source in any case; the
  selector decides which of a row's values follow it. `caption`, a `:text`
  input, stays translated; a field neither listed nor text is copied once.
- `{:module, "hero-banner", [:layout, :dark]}` makes two variables of the
  module with uid `"hero-banner"` follow the source, in every block built from
  that module. A `:layout` variable on another module stays each language's
  own. Keys may be atoms or strings.

When a translation holds a different value for a source-controlled field, its
pending version sets the source's value and lists it as a **shared update** for
the editor to accept.

##### Selector reference

`source_controlled_fields` takes three kinds of selector:

- **Top-level attributes, assets and `belongs_to` relations**, as plain names.
  Assets always follow the source; listing them documents it.
- **Fields of an owned subform**, as `subform: [fields]`. The subform must be a
  `has_many` with `cast: true`, or an `embeds_many`, whose rows are matched by a
  `uid` attribute (`trait :ensure_uid`); the fields must be inputs of that
  subform in the form. `id`, `uid`, `sequence`, timestamps and foreign keys
  identify rows and are refused. Other fields of the row stay the
  translation's own.
- **Variables of one block module**, as `{:module, "uid", [keys]}`, where `uid`
  is the module's `uid` (the identifier `Brando.Content.Definition` uses). The
  same variable key on another module stays language-specific. Modules are
  content, so these are checked at runtime: `Brando.Translations.check_config/1`
  lists a module uid or variable that does not exist, for example after a
  module was renamed or its variable removed. Until the selector is fixed, such
  a variable is simply not source-controlled.

Selectors are validated when the Blueprint compiles; an unknown field, a
non-owned relation or an identity field raises. So does listing the same
subform or module twice, `source_controlled_fields` without
`mode: :synchronized`, and `mode: :synchronized` with `alternates: false`.
Variables of table rows and of nested subforms cannot be addressed, and a
subform whose rows have no `uid` is not synchronized.

#### Language-controlled assets

Assets follow the source by default. When one should differ per language — a
listing image with text in it, a document in each language — list it in
`language_controlled_fields`:

```elixir
trait :translatable,
  mode: :synchronized,
  source_controlled_fields: [:year],
  language_controlled_fields: [:listing_image, :brochure]
```

The asset is copied when a translation is created, then each language keeps its
own: a source save doesn't change it, and it stays editable in the translation's
form. `:image`, `:file`, `:video` and `:gallery` assets can be listed, and a
relation to the schema itself, such as a page's `:parent`, for a hierarchy that
differs per language. Everything else is already each language's own unless it
is source-controlled.
Listing a field in both options, or using the option without
`mode: :synchronized`, raises when the Blueprint compiles. Media inside blocks
always follow the source.

#### Synchronized pages

Pages are independent by default. To synchronize them, configure Brando's Page:

```elixir
config :brando, Brando.Pages.Page,
  translatable: [
    mode: :synchronized,
    source_controlled_fields: [:template, :is_homepage, :has_url, :css_classes]
  ]
```

The `translatable` keyword takes the same options as the trait. The fields
above are a sensible start: the template and page flags are the same in every
language, while `uri`, `title` and the meta fields stay translated. Run
migration 182 first.

The config is read at runtime; no recompile is needed. In a tenant
installation, `translatable_sites` sets it per site key and replaces
`translatable` for that site:

```elixir
config :brando, Brando.Pages.Page,
  translatable: [mode: :independent],
  translatable_sites: %{"acme" => [mode: :synchronized, source_controlled_fields: [:template]]}
```

Brando validates these at boot like a Blueprint's own options and refuses to
start on an invalid one. Other Blueprints configure translation in their own
code; only a Blueprint that declares `trait :translatable, runtime_config: true`
reads this config.

A page's parent follows the source, pointed at the parent's version in the
translation's language. When the parent has no version in that language yet,
the translation keeps its own parent and shows the parent as awaiting
translation; creating the parent's translation fills it in. For a hierarchy
that differs per language, list `:parent` in `language_controlled_fields`.

A fragment block in a translation embeds the fragment's linked version in the
translation's language, and the source's fragment while there is none; linking
or creating that version moves the block over to it, and unlinking it moves the
block back. Fragments themselves are
separate entries, synchronized or not on their own (see below).

#### Synchronized fragments

Fragments are independent by default. Configure Brando's Fragment the way the
Page is configured:

```elixir
config :brando, Brando.Pages.Fragment, translatable: [mode: :synchronized]
```

It takes the same options, `translatable_sites` included. A synchronized
fragment works as a synchronized page does: **Create a translation** in its
form, the same work list, and its blocks, media and links following the
source. Its parent key and key are source-controlled: every language version
has the same keys, so a template finds each one by its language, and a key
changed in the source moves to the translations when they are saved. The
fragment's page is source-controlled too, whatever the config lists: a
translation belongs to its page's version in its own language (or to the
page itself when that page is in the translation's language), and to no page
until that version exists, never to the source-language page; a config that
lists `:page` in `language_controlled_fields` is refused at boot. Deleting a page with its
fragments is refused as a whole while one of them is the source of
synchronized translations, as deleting the fragment is.

To synchronize the fragments of a site that has them in several languages:

1. Run migrations 182 and 244 (`mix brando.gen.migrations`, then
   `mix brando.migrate`).
2. Run `mix brando.fragments.pair --apply` (above) to link the existing
   fragments that share their keys. They stay independent: linking is not
   synchronizing.
3. Add the config and deploy. Nothing changes on the public site: each
   language still prints its own fragment.
4. For each key to synchronize, as for any existing translation (see the
   next section): move the other language's fragment to the trash (it holds
   its language while it is out of the trash, linked or not), open the
   source-language fragment, **Create a translation** for that language,
   move the text over from the old fragment and publish the translation. From
   the delete until that publish, the template prints nothing for that
   language: the new translation is an unpublished draft. Delete the old
   fragment for good once the translation is published.

#### Adding synchronized mode to an existing Blueprint

1. Make sure framework migration 182 has run: `mix brando.gen.migrations`,
   then `mix brando.migrate` (and `--tenants` for named environments).
   Synchronized mode adds no columns to your own tables — `language` and the
   alternates relation come from `trait :translatable` — so no Blueprint
   migration is needed.
2. If the schema was not translatable before, adding the trait adds both: run
   `mix brando.gen.blueprint_migration` for it. The generated migration leaves
   `language` empty on existing rows, and it is required, so add a backfill to
   it before running it, for example
   `execute "UPDATE projects SET language = 'no' WHERE language IS NULL"`.
3. Translations start as a copy of the source, so the context needs a
   duplicate mutation (`mutation :duplicate, {Project, change_fields: [...]}`).
   Without one, **Create a translation** isn't offered.
4. A source-controlled `slug` is the same in every language, so its uniqueness
   must be per language: `unique: [prevent_collision: :language]`, and a
   Blueprint migration for the index.
5. Run `mix brando.identifiers.sync`, so identifiers made before the schema
   was translatable get their entry's language. Link pickers filter on it.
6. Add `mode: :synchronized` and any `source_controlled_fields`, and deploy.
   Call `Brando.Translations.check_config(MyApp.Projects.Project)` against the
   target database: it returns `[]`, or the module uids and variables in your
   selectors that do not exist there.
7. Nothing changes for existing entries until an editor acts. An entry joins a
   group when it gets its first translation through **Create a translation**,
   and becomes that group's source.

Translations that already exist, linked as alternates, stay independent. They
are not joined to the group and not offered under **Create a translation**,
and there is no way to adopt one: its blocks were copied on their own and have
their own sync identities, so the sync could not pair them with the source's.
To synchronize such a pair, create the translation with **Create a
translation**, move the text over from the old version, publish it, and delete
the old one. Or leave it independent; both kinds can live in one schema.

From code, `create_target/4` returns `{:error, :language_exists}` for a
language the group already has or that an independent version holds, and
`{:error, :language_in_trash}` for one whose version is in the trash.
Deleting the old version frees its language; a version in the trash frees it
once it is deleted for good. `replace_trashed_target/5` is what the admin calls
once the editor has confirmed: it deletes the version in the trash for good
(`Brando.SoftDelete.Query.purge_entries/3`, the trash purge's path, the
context's `before_purge/2` included) and creates the translation, in one
transaction. It takes permission to delete that version, and returns
`{:error, :language_in_trash}` without it.

#### In the admin

- **Creating a translation.** An entry of a synchronized schema lists the
  languages it has no version in. Creating one makes an unpublished copy,
  linked as an alternate, and the entry becomes the source. The copy starts
  from the source's text (the context's duplicate marks copies, a translation
  doesn't), and every text it copied is marked **translate**, as if it were
  new: each text of the Text class in [What follows the source](#what-follows-the-source)
  that is not empty. Translating one, or marking it **Reviewed**, resolves
  it. A text the source changes before it is translated stays marked
  translate, not review, and the translation gets the source's new text to
  translate. Entries a duplicate would copy along, such as a page's child
  pages and fragments, are left out: each is translated on its own. Languages
  that already have an independent alternate, or an entry with the entry's
  `matched_by` values, are not offered; joining existing
  alternates to a group is not supported.
- **Editing a translation.** Opening a translation loads its pending version
  into the form as unsaved changes and lists the work: text to translate, text
  to review, values updated from the source, links waiting for a translation,
  and structural changes with no text work. Link items name the entry they now
  point at or wait for. A pending version computed before the translation last
  changed (a published revision, a scheduled release) is recomputed first, so
  applying it never overwrites that change. The affected blocks and fields are
  marked. Mark text as **Reviewed** when it needs no change. Saving writes the
  pending version as far as the form shows it and resolves only the work of
  the version the editor loaded; what was not done stays open. A form without
  some of the entry's fields, such as one without its block fields or without
  an input for a source-controlled value, saves what it holds and keeps the
  rest as it was: that part stays pending, and its work, the text in a block,
  picture or link the save left as it was included, stays open for a form
  that shows it. A published translation updates on save; a new one stays a
  draft until it is published.
- **One version at a time.** The form loads a pending version when it opens
  (or reconnects) and again after its own save, never while the editor
  works. When the source is saved again meanwhile, the panel says so: the
  newer changes are loaded when the translation is saved. Editors in the
  same translation share the version its unsaved block changes are built
  on: a second editor who opens it, or an editor who reconnects while others
  are still in it, gets that version, not a newer one. When another editor's
  save loads newer changes from the source into the blocks, an editor with
  no unsaved changes in the other fields gets them there too, in place, and
  the panel says so; an editor in one of those fields gets them on leaving
  it. An editor with unsaved changes in the other fields keeps them, but the
  form refuses to save until they press **Load the newer changes** in the
  panel, which replaces those changes and keeps their block changes. Either
  way, what other editors have typed and not saved stays in the form, and a
  text marked reviewed stays marked only if the source has not changed it
  again.
- **Translate with AI.** Where an AI provider is configured
  (`Brando.AI.configured?/1`), a translation's work list has **Translate with
  AI**, for every open *translate* and *review* text, and an AI action on each
  of those items for that text alone. Translating every text leaves out what
  the editor has worked on: items ticked **Reviewed**, and texts in the form
  that are no longer the pending version's (typed, or filled by an earlier
  run); an item's own action translates it in any case. An address (a
  link's URL) has no AI action and is never sent, nor is a text locked for
  this editor (a read-only field, or a subform in a fieldset only superusers
  may change) or one the form has no input for or hides. It runs in the
  background while the form
  stays usable, and fills the form with the texts as unsaved changes: nothing
  is saved, no work is resolved and no pending version is written. Each filled
  item is marked **Filled in by AI** until the save, which resolves the items
  as it does for typed text. For a *review* item the model gets the source's
  text and the translation as the form has it, and brings the translation up
  to date; where the item has the source's text from before the change, the
  model gets that too, and is asked for the smallest change to the
  translation that follows the source's change. A text whose reply lost the source's HTML tags or template
  placeholders is not filled in, and its item says why; a text changed during
  the run, in this form or by another editor, keeps that text. Fields hidden
  during the run keep their values. Taking over editing in another tab
  discards the previous tab's pending replies. If the call
  fails, or the source changes while it runs, nothing is filled in and the
  work list says so. The filled texts reach other editors of the entry as
  typed text does. A gallery's per-image texts are translated in the block:
  their items stay in the work list without an AI action, and are not sent.
- **What a translation cannot change.** Structure, media and source-controlled
  values follow the source. Their controls are hidden or disabled in a
  translation, and the save refuses any change to them, whatever sent it.
  Picture, video, file and gallery refs in blocks, and image, file, video and
  gallery variables, in blocks and among the entry's own variables, show
  their media with a note that it follows the source, and take no upload,
  replacement, removal, image edit or dropped file; an empty one says the
  source has none. Their settings stay open for what the
  translation keeps: a picture's caption, credits and alt text, a video's
  caption, a file's title, link label and description, and each gallery
  item's texts. A gallery variable, in a block or among the entry's own
  variables, saves its gallery as it is edited, before the entry is saved;
  in a translation it holds the source's gallery and refuses those edits.
- **Source changes during editing.** If the source is saved again while a
  translation is open, the save still writes what the editor reviewed, then
  loads the newer changes into the form and says so. Newer work stays open.
- **Minor corrections.** On the source, **Save minor text corrections** saves
  without asking the translations to review changed text. Structure, shared
  values and new text are still synchronized, and work already open stays.
- **Make independent** stops a translation from following its source. It keeps
  its content, its unsaved changes and its alternate link. Each gallery it
  shares with the source, a gallery variable's above all, gets a copy of its
  own, with the same media in the same order and each item's settings, so
  editing it changes only the translation. The open form's gallery variables
  take their copies. A gallery block whose ref was saved holding the source's
  gallery, by a Brando version that did not yet copy refs added by the
  source, takes its copy when the translation is opened again, and the form
  says so. A save that writes the source's gallery
  back (from a form opened before, or a restored revision) is followed by a
  new copy.
  **Make source** hands the source role to a translation; the others follow it
  from its next save, and the galleries they share stay shared. Neither
  publishes anything. The source itself cannot be made independent; make
  another version the source first.
- **Deleting a source** from its row in a listing opens a dialog that lists
  its translations (published ones apart, since deleting them takes them off
  the site, and those already in the trash) and asks what becomes of them:
  - **Delete them with it**: the source and every translation not in the
    trash go to the trash together, in one transaction, each with its own
    activity line, keeping their place in the group
    (`Brando.Translations.delete_with_translations/5`). Restoring the source
    restores the translations deleted with it, as one, and queues a
    synchronization of the group; a translation trashed on its own before
    stays in the trash with its own date. While the source is in the trash,
    a translation is not restored on its own; deleting one for good is
    allowed. In a schema without a trash they are all deleted for good.
  - **Keep them, and make this one the source**, or **Keep them as
    independent entries** (`delete_keeping_translations/6`): the role moves
    to the translation chosen (the source goes to the trash as its
    translation), or every translation is made independent; then the source
    is deleted. A translation already in the trash stays there, made
    independent.

  Each choice is offered only when the editor may do it to every version it
  changes: delete (and publish, for a published one) each translation, or
  update the ones kept. A translation the editor may not read is counted, not
  named, and rules out deleting them with it. The delete runs against the
  group as the dialog showed it: a translation added, published, made
  independent or made the source since deletes nothing and opens the dialog
  again. Deleting several selected rows still refuses a source
  (`{:error, :group_has_synchronized_members}` from the delete mutation), as
  does a delete with no choice. A deleted source takes its group with it; the
  independent versions stay, outside any group.
- **Deleting a translation.** In the trash, a translation keeps its place in
  the group and its language: restoring it puts it back as it was, with its
  pending version and work. Meanwhile the listing leaves it out of the
  language versions. **Create translation [XX]**, **Create and translate
  [XX]** and the form's **Create a translation** still offer its language,
  and ask first: confirmed, the version in the trash is deleted for good (its
  group member, pending versions, work and alternate link go with it) and the
  new translation is created, in one transaction; a failed create leaves it
  in the trash. Replacing it takes permission to delete entries of that type;
  without it the editor is told the version is in the trash, to restore it
  from there. A proposal's `create_translation` is refused
  (`{:error, :language_in_trash}`): only the admin deletes for good.
  Deleted for good (the trash emptied, or deleted in a schema without a
  trash), it leaves the group with its pending versions, work and alternate
  link, and its language can be translated again.
- **From the Assistant and MCP.** A proposal's `create_translation` creates a
  translation as **Create translation** does, once the proposal is reviewed and
  applied ([Language versions](content_assistant.md#language-versions)).
- **Listings** show each language version of a synchronized entry with its open
  work — to translate, to review, links waiting, or updated from the source —
  linking to that version. Only versions the user may read are listed. Next
  to **Create translation [XX]**, where an AI provider is configured,
  **Create and translate [XX]** creates the translation the same way, opens
  it, and starts Translate with AI there; the editor checks the texts and
  saves. Closed without saving, the translation stays created and
  untranslated.
- **Assistant and MCP.** The `translation_work` tool reads a translation's
  open work from its pending version, as units with the source's text, the
  translation's and their format, and a source's missing languages ([Content
  assistant: Translation work](content_assistant.md#translation-work)). A
  proposal's `translate` operation answers it: once the proposal is reviewed
  and applied, the translation is saved as its form saves it and the answered
  work is resolved ([Translating with a
  proposal](content_assistant.md#translating-with-a-proposal)). Its
  `sync_translation` operation takes the links, media and values the source
  changed, as saving the form without editing does ([Taking the source's
  changes](content_assistant.md#taking-the-sources-changes)).

#### From code

`Brando.Translations` is the API the admin uses:

```elixir
alias Brando.Translations

{:ok, norwegian} = Translations.create_target(Project, english.id, "no", user)
{:ok, _member} = Translations.make_independent(Project, norwegian.id, user)
{:ok, _member} = Translations.transfer_source(Project, norwegian.id, user)

# %{entry_id => [%{language: "no", entry_id: 8, role: :target, ...}]}
Translations.listing_status(Project, entries, user)
```

`create_target/4` duplicates the source through the context's `duplicate_*`
mutation as an unpublished draft that keeps each block's `sync_uid`, links it
as an alternate and computes its first pending version, with every copied
text marked to translate. Its slugs follow their uniqueness: one unique per
language keeps the source's value, any other gets the language appended (see
[Preventing collisions](blueprint_fields.md#preventing-collisions)), and the
translation keeps the slug it is created with. It
refuses a language the group already has. For a translation meant to start
from the source's text as it is, such as a language variant that differs in a
few places, pass `mark_translate: false`:
nothing is marked, and only later source changes raise work.

```elixir
{:ok, norwegian} = Translations.create_target(Project, english.id, "no", user, mark_translate: false)
```

`Brando.Translations.Work` reads the same work as units for a client to
translate: `translation_units/2` for a translation, `new_translation_units/2`
for a language a source has no version in yet, `batch/5`, and `token/2` with
`check/4`, which refuses an answer whose source text changed since it was
read, whose keys do not match, or whose text lost the source's markup or
placeholders.

`Translations.save_work/5` saves answered work as the translation's form
saves it: the pending version with the texts written in at their keys,
`check_target_save/4`, the context's update with `editor_review: true`, then
`target_saved/3` with every answered key acknowledged, so each answered work
item is resolved. It returns the items it resolved, which
`Translations.reopen_work/3` opens again after the texts are put back.

```elixir
{:ok, %{entry: entry, resolved: items}} =
  Translations.save_work(Project, norwegian.id, %{texts: %{"title" => "Tittel"}, acknowledged: []}, user)
```

`make_independent/3` returns `{:error, :is_source}` for the source, and
copies the galleries the translation shares with the other versions of its
group; `transfer_source/3` takes only a synchronized translation.

A translation made independent before `make_independent/3` copied galleries
still shares them: `mix brando.doctor` lists it under "Translation
galleries", and `mix brando.translations.split_galleries` (or
`Translations.split_shared_galleries/3`) gives it its copies.

Every duplicate and translate action copies an entry this way. Galleries on
gallery assets, refs and vars are cloned, so the copy gets its own gallery. Owned `has_many` and `has_one`
rows (subforms with `cast: true`) are copied with the same `uid`. At any depth,
a copied row's own owned rows and blocks are copied too, and its galleries
cloned. The related entries of an `:entries` relation are linked from the copy
as well. A copy into another language (a translation, or the listing's
duplicate and translate to a language) links their versions in its language,
its subform rows' related entries included, and leaves out one that has none
yet. Duplicating several selected entries to a language links an entry copied
in the same batch as its copy, and a toast says how many links were left out.
A translation, or such a batch, links an entry listed among its own related
entries as its copy. In a
translation, a context's own `change_fields` for the relation take its place;
the listing's copies replace the context's `change_fields` with their own.
Later changes to the source's related entries are not synchronized. Linking rows such as alternates are dropped instead of being
moved to the copy. A `belongs_to` relation points at a row the copy shares with the
original. `change_fields` passed as override options to a `duplicate_*`
mutation normally replace the context's own; with `merge_change_fields: true`
the context's handlers are kept for every field the override does not name.

## Single-language sites

<!-- usage-rules:start topic="i18n" -->

When `:languages` has one entry (in `:multi`, when the site has one
language), the admin hides the language select on pages,
fragments, menus and global sets, and the sidebar's content-language switch.
New entries still get the editor's content language. Hide the language input
of your own Blueprints the same way:

```elixir
input :language, :select,
  options: :languages,
  hidden: &Brando.I18n.SingleLanguage.single_language?/1
```

Capture it from `Brando.I18n.SingleLanguage`, not `Brando.I18n` (which
delegates to it). A capture in a Blueprint is a compile-time reference, and
`Brando.I18n` reaches back into `Brando`, which puts every Blueprint that
captures it in a compile-connected cycle. `SingleLanguage` only reads
`Brando.Languages`, which reads the application environment and the tenant
cache.

<!-- usage-rules:end -->

## Translated strings in one field

Short texts that belong to one record but differ per language, such as an
image's alt text, use the `:i18n_string` attribute type: a jsonb map of
language → text. Edit it with the `:i18n_text` or `:i18n_textarea` input,
which shows one tab per language:

```elixir
attribute :caption, :i18n_string

input :caption, :i18n_text, label: t("Caption"), languages: :content
```

The tabs list the admin languages unless `languages: :content` selects the
site's content languages; use `:content` for text shown on the site. A
language's tab is marked, in amber, only while another language has text, so
an empty optional field shows no marks. Blank values are stored as `nil`.

Stored translations whose languages are not in the configured tabs are kept
when the form is saved. Removing a language from the configuration does not
delete its text. Clearing a language's editable input still clears that text.

Read one language with `Brando.Type.I18nString.get(value, language)`. It
returns that language's text, else the default content language's, else
`nil`. A plain string, from older data or a form that sent one value, casts
under the default content language. In Liquid, use the `i18n` filter; see
[Images, files, and galleries](media.md#render-responsive-images) for image
texts.

## Route the requested language

The generated `put_locale` plug uses `Brando.I18n.parse_path/2`, against the
request's site's languages in `:multi`. With the config
above, `/` becomes `{ "en", ["index"] }`, `/about` becomes
`{ "en", ["about"] }`, and `/no/om` becomes `{ "no", ["om"] }`.
An unknown first segment remains part of the path in the default language; it is
not accepted as a new language code. Page controllers must include the language
in the query, as shown in [Pages](pages.md#resolve-and-render-public-pages).

<!-- usage-rules:start topic="i18n" -->

For application-specific routes, declare both paths before `page_routes()`:

```elixir
scope "/", assigns: %{language: "en"} do
  pipe_through :browser
  get "/news", MyAppWeb.PostController, :index

  scope "/no", as: :no, assigns: %{language: "no"} do
    get "/nyheter", MyAppWeb.PostController, :index
  end

  page_routes()
end
```

Use `conn.assigns.language` in the controller's content filter. In HEEx:

```heex
<a href={Brando.I18n.Helpers.localized_path(@language, :post_path, [@conn, :index])}>
  {gettext("News")}
</a>
```

`localized_path/3` selects the localized router helper when present. If it is
absent at the requested arity, it falls back to the unscoped helper. If neither
exists, it returns `"/<url cannot be localized>"`; treat that as a routing error.
For catch-all pages, use `Brando.Blueprint.URL.resolve(page)` so the page's URL
rules handle language prefixes. A generic `page_path` helper alone does not
translate the URI or prepend a locale to its path list.

<!-- usage-rules:end -->

If English should live under `/en`, set `scope_default_language_routes: true`
and give custom English routes an `as: :en` scope too.

On a multi-site installation (`tenancy_mode: :multi`) the unprefixed routes are
each site's default language's, so every language the installation configures
needs its prefixed scope, the installation's default included, as
[Languages per site](tenancy_and_environments.md#languages-per-site) explains:

```elixir
scope "/" do
  pipe_through :browser
  get "/news", MyAppWeb.PostController, :index

  scope "/en", as: :en do
    get "/news", MyAppWeb.PostController, :index
  end

  scope "/no", as: :no do
    get "/nyheter", MyAppWeb.PostController, :index
  end

  page_routes()
end
```

Here `put_locale` in the `:browser` pipeline gives each request its language,
from the path and the request's site. An `assigns: %{language: …}` on the
unprefixed scope would give those routes one language on every site.

Without `put_locale` in the pipeline (an installation without the CMS site),
give each prefixed scope its `assigns: %{language: …}` and the unprefixed scope
none. The controller then takes the language from the request's site: the one a
controller from `mix brando.gen` reads is `conn.assigns[:language]` when a plug
set it, else `Brando.Languages.default_language/0`, which answers for the site
once its own `plug Brando.Plug.Tenant` has resolved it, so keep that plug ahead
of the actions.

Host-based language
selection is available through `plug :put_locale, by_host: %{"example.no" => "no"}`;
keep tenant/domain resolution and controller path handling consistent with that
choice.

<!-- usage-rules:start topic="i18n" -->

## Emit language alternatives

Preload `:alternate_entries`, call `Brando.Plug.HTML.put_hreflang(conn, page)` in
the controller, and place this in the HTML head:

```heex
<Brando.HTML.render_hreflangs conn={@conn} />
```

It emits canonical and alternate URLs from the entry URL definitions. Inspect
the generated URLs rather than constructing translations by swapping a prefix:
`/about` and `/no/om` have different slugs. Do not link unpublished translations
from your own language switcher; filter its candidates for public eligibility.

## Translate interface strings with Gettext

Backend modules use `Gettext.Backend`; callers use `Gettext` with that backend:

```elixir
defmodule MyAppWeb.Gettext do
  use Gettext.Backend, otp_app: :my_app, priv: "priv/gettext/frontend"
end

# In a controller or component that uses translated strings:
# use Gettext, backend: MyAppWeb.Gettext
```

Extract literal strings, then merge each consumer catalogue:

```bash
mix gettext.extract
mix gettext.merge priv/gettext/frontend --locale no
mix gettext.merge priv/gettext/backend --locale no
```

Translate the generated `.po` files and recompile. Frontend and admin catalogues
are separate; editing the frontend catalogue will not translate admin labels.
See [Migrating from 0.53 or 0.54](migrating_from_053.md) for upgrading older Gettext callers.

<!-- usage-rules:end -->

Finally, visit both language routes, reopen both pages, and inspect their menu,
identity, metadata, and alternate links. Also request a missing Norwegian page:
it should use your missing-page behavior, not silently serve English content.
