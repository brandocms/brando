## 3. Disconnect/reconnect recovery — VERDICT: tested, but narrowly, and only in Playwright

- **`e2e/e2e/playwright/tests/blocks/block-recovery.spec.js`** — the only recovery test in the repo.
  - Test 1: `window.liveSocket.disconnect()` → `waitForTimeout(500)` → `window.liveSocket.connect()` → asserts one block still present and textarea value survived. This is a **real LiveView reconnect** (Phoenix's own reconnect/rejoin, not process kill) exercised through the browser's actual liveSocket.
  - Test 2: disconnect → connect → `page.goto('/admin')` (fresh navigation) → re-enters create form → asserts no "already associated" crash from stale sessionStorage. Covers a stale-state regression, not general recovery.
  - `block-live-preview.spec.js:83` also calls `liveSocket.disconnect()` but only to test preview iframe re-render after reconnect, not form/block data recovery.
- **No CDP network emulation, `context.setOffline`, `context.route` abort, or process-kill anywhere in `e2e/e2e/playwright/tests`** — grep for `setOffline|emulateNetworkConditions|Network\.|context\.route` returned zero matches outside the `disconnect()` calls above. So: no test for actual network partition (vs. the JS-level `liveSocket.disconnect()`, which is a clean, cooperative disconnect — not a TCP drop, not a killed server-side LV process).
- **No test kills the server-side LiveView process** (no `:sys.terminate`, no proc lookup+kill via `/eval`, though `evalPlug`/`evalLV` helpers in `utils.js` exist and could reach into the process for this).
- **No sessionStorage-recovery-succeeds test** — only the negative case (stale storage must NOT falsely trigger recovery). There's no positive test proving sessionStorage recovery actually restores unsaved form/block edits after a genuine mount replacement.
- **ExUnit side**: zero disconnect/recovery tests — expected, since `Phoenix.LiveViewTest` doesn't model transport drops without a live socket, and none exist here (see Q1/Q3).

## 4. Can LiveView process death + remount be tested with `Phoenix.LiveViewTest`?

Concretely for this codebase: **yes for mount/render assertions, no for the specific "kill and remount preserving edits" scenario without new harness work.**

- `Phoenix.LiveViewTest.live/2` + `render_leave`/killing the pid to force `handle_disconnect`-style remount IS possible in principle (`GenServer.stop(view.pid)` then `Phoenix.LiveViewTest.live/2` again to a fresh mount, comparing DOM/session).
- **Blockers found in this codebase**:
  - Zero existing `live(conn, ...)` scaffolding for any admin form route — there is no `test/brando_admin/**/*_live_test.exs` at all (confirmed by the `ConnCase`/`live(` grep above and by `Glob` of `test/brando_admin/` showing only component-render tests plus `test/brando_admin/view/project_list_live_test.exs`, which is worth checking as the one exception — but even that title suggests a listing view, not a form/block editor).
  - The block editor's "sticky" client JS state (`DOM.putSticky` for presence locks per `AGENTS.md`) and the op-store/PubSub multiuser sync are JS-side and client-socket-side; `Phoenix.LiveViewTest` has no browser DOM/JS hook execution, so recovery behavior that depends on `liveSocket.js` reconnect semantics (as in `block-recovery.spec.js`) is **fundamentally untestable in ExUnit** — it requires a real browser transport, which is why the only recovery coverage is Playwright.
  - `BlockField`'s in-memory op store (`Ops`) is tested directly and thoroughly (`blocks_cross_parent_move_test.exs`), but never through a mounted component's `handle_event`/`handle_info` — so a test asserting "kill the LV process, remount, unsaved block ops recovered from sessionStorage" cannot be assembled from existing pieces; it would need: (a) a route/session fixture for a page-create or page-update mount, (b) a seeded module/blueprint (the E2E seeds already provide "05 LIVE PREVIEW TEST" etc., but ExUnit's `Factory` does not obviously seed matching content modules — would need to check `test/support/factory.ex` module factory further), (c) presence/PubSub setup since BlockField syncs via topics.
- One exception worth flagging: `test/brando_admin/view/project_list_live_test.exs` — this IS a real LiveView test using `live(conn, ...)`? Not confirmed in this pass (only matched on `Phoenix.LiveViewTest` import, not necessarily `live/2` call) — flag for the planner to check directly if listing-view coverage patterns are reusable for form/block routes.

## 5. Upload paths testable without real S3/Mux/Bunny

- `Brando.Uploads` pure-function boundary is well covered without network:
  - `test/brando/uploads_test.exs` — `validate_intake/4`, `manager_max_file_size/0`, `initiate/4` (server vs presumed-direct transport decision), `validate_provider_video_intake/2` (mux/bunny gate/strategy/size/mime), `resolve_video_config/1`, `store_upload/4` error normalization, `presign_put/2` (constructs and signs a URL against a fake `S3Config` — **no real network call**, just AWS SigV4 math against static test keys), `validate_direct_object/3` (HEAD-response validation against a hand-built response map), `max_concurrent_transfers/0`, `direct_transport?/1`, `direct_video_transport?/1`.
  - `test/brando/videos/upload_test.exs`, `test/brando/videos/uploaders/cloudflare_test.exs`, `test/brando/videos/uploaders/bunny_test.exs` — webhook-handling logic (e.g. "late processing webhooks cannot regress a ready video", "terminal errors ignore later stale provider status") tested by calling `Bunny.handle_webhook/1` directly with a synthetic payload against a DB-seeded `video` record. **No Bypass, no Mox, no HTTP interception** — these tests only reach the parts of the uploader that don't make outbound calls (webhook receipt + status-transition logic). Nothing here exercises the actual outbound presigned PUT, Mux asset creation call, or Bunny library API call.
- **No mocking boundary exists for outbound provider calls.** Grep for `Mox|defmock|bypass|Bypass` across `test/` returns only `test/brando/blueprints/relations_test.exs` and `test/brando/blueprints/runtime_regression_test.exs`, neither upload-related (false-positive matches, likely on unrelated words — worth the planner double-checking if precise mock coverage is claimed elsewhere). **There is no `@callback` behaviour wrapping S3/Mux/Bunny HTTP clients that a Mox mock implements**, contradicting Iron Law 4/skill guidance to mock only at a defined boundary — currently there is no such boundary abstraction to mock at all for outbound calls.
- Real upload flow (multipart consume → CDN copy → var/asset commit → persistence) is **only** covered end-to-end in Playwright against the live (test-env) server, e.g. `block-var-uploads.spec.js`, `page-vars-upload.spec.js`, `block-media-save-persistence.spec.js`, `block-gallery-image-replace.spec.js`, `block-image-editor.spec.js`, `assets/image-editor.spec.js`, `assets/galleries.spec.js`, `projects/file-field-sync.spec.js` — all using real file fixtures (`e2e/e2e/playwright/fixtures/image.jpg`, `image2.jpg`, `test.pdf`, `video.mp4`) and a real running Phoenix app (presumably local/dev CDN config, not real S3/Mux/Bunny — config not verified in this pass).

## 6. Ranked missing tests (recovery / upload-commit-orphans / block-changeset focus)

1. **LiveView process death + remount for the block/page form, ExUnit-level.** Harness needed: a `test/brando_admin/**/*_live_test.exs` using `Phoenix.LiveViewTest.live/2` against a real admin page-create/update route, a factory-seeded content module (check `test/support/factory.ex` for module/blueprint factories — not yet confirmed to exist), and killing/remounting the view pid to assert state reconstruction. This is the single biggest gap: it is the only way to assert server-side recovery logic deterministically and fast, instead of only via slow, flaky-prone Playwright disconnect timing (`waitForTimeout(500)`).
2. **Positive sessionStorage-recovery test in Playwright** — only the negative ("stale storage must not falsely trigger") exists; nothing proves recovery actually restores unsaved edits after a genuine full-page reload/remount (not just a `liveSocket.disconnect/connect` cycle, which doesn't destroy the LV process). Harness: extend `block-recovery.spec.js` with a hard `page.reload()` (not just socket toggle) after unsaved edits, asserting restoration.
3. **True network-partition recovery** (CDP `Network.emulateNetworkConditions` / `context.setOffline`, not the cooperative `liveSocket.disconnect()`) — currently zero coverage of what happens when the WS drops involuntarily (server restart, proxy timeout) rather than being told to disconnect. Harness: Playwright CDP session or route abort on the websocket upgrade request.
4. **Upload commit/orphan coverage at the DataCase level** — `orphaned_blocks_test.exs` covers block orphaning but nothing analogous exists for **asset/upload orphaning** (e.g., an image uploaded via var/asset field, then the entry save fails or the var is reset — does the uploaded file/DB row get orphaned or cleaned up?). Only Playwright partially covers this via `block-var-uploads.spec.js`'s reset tests, and those assert UI state, not DB/storage-row cleanup. Harness: DataCase test hitting `Uploads`/whatever commits an uploaded asset onto a var/changeset, asserting no orphaned `Image`/`GalleryImage`/`File` row remains after a failed or reset save.
5. **A behaviour-wrapped provider client + Mox coverage for outbound S3/Mux/Bunny calls** — per Iron Law 3/4, the codebase should wrap these behind an internal module with a `@callback`, then Mox-test the actual commit/failure paths (e.g., presigned PUT succeeds but `validate_direct_object` HEAD check fails mid-flow — is that exercised anywhere against a live-ish mock? Currently no). Today only the pure decision functions around these calls are tested; the actual call-and-handle-response path is only reachable via full Playwright E2E.
6. **Multi-root/multi-block-type changeset interaction under partial failure** — `blocks_cross_parent_move_test.exs` covers moves/edits/deletes/inserts individually but not a save where one root changeset fails validation while siblings are valid (does the whole `put_assoc(:entry_blocks, ...)` roll back correctly, and does the block-editor's ops store reconcile after an `{:error, changeset}` return?). Not found in DataCase or LiveView layer.

- No `@tag :skip`, `@moduletag :skip`, or `ExUnit.Case, async: false` markers found flagged in scanned files beyond the deliberate `async: false` justified by global `Application.put_env` mutation (documented inline in `uploads_test.exs`, `orphaned_blocks_test.exs`, `blocks_cross_parent_move_test.exs`, `bunny_test.exs`) — these are correct per Iron Law 1 exception, not smells.
- Playwright: `block-recovery.spec.js` and `block-multiuser-sync.spec.js` rely on fixed `waitForTimeout` values (500ms, 600ms, 750ms, 1200ms, 1500ms) rather than event-based waits, with comments acknowledging debounce/settle timing (e.g. "debounce flush → op emitted", "blur → snapshot ships → B merges"). These are timing-fragile by construction — not currently reported as flaky, but they are the highest flake-risk tests in the repo and a CI slowdown would likely break them, per the codebase's own `waitForPreviewUpdate` comment about a prior sleep-based test failing on a slower CI runner (`utils.js` lines 137-141, 149-160).
- No explicit skip/xfail markers found in the `e2e/e2e/playwright/tests/**` files checked directly (block-recovery, block-multiuser-sync, block-var-uploads); a full-repo grep for `test.skip|test.fixme|xit(` was not run due to turn budget — flag as unverified.

## 8. Test quality assessment where forms are covered

- **`error_display_test.exs`**: high quality — builds changesets by hand with explicit `used_input?` control (untouched vs submitted), documents *why* `Map.put(:action, :validate)` is required, tests a non-Blueprint struct fallback path deliberately. Good ExUnit idiom, no over-mocking (uses real changesets, no mocks at all).
- **`blocks_cross_parent_move_test.exs`** / **`orphaned_blocks_test.exs`**: excellent — real DB via `Factory.insert`, exact replication of production save mechanics, assertions pinned to row identity (`moved.id == original_child_id`) rather than just "it worked," which is precisely the kind of assertion that catches delete+reinsert vs UPDATE regressions. These would catch most block-changeset regressions the audit cares about.
- **Gap in quality, not correctness**: none of these tests go through the actual `BrandoAdmin.Components.Form.BlockField` LiveComponent's `handle_event`/`update` callbacks — they call `Ops` and `Blocks.changeset` directly. A regression introduced in BlockField's event handling (wrong op dispatched, wrong assign updated) would **not** be caught by any ExUnit test today; only Playwright would catch it, several minutes later and with much less precise failure output.
- **`uploads_test.exs`**: good coverage of pure validation/decision functions with clear regression comments (e.g., "handle_upload/4 leaks 3/4-tuple errors"), but by construction cannot catch integration failures (actual S3 signature rejected by real S3, actual multipart consume failure) since there's no real network boundary exercised or mocked.
- **No factory-vs-build misuse observed** in the files read — `Factory.insert` used deliberately where DB rows are required (block/page persistence tests), consistent with Iron Law 5.
